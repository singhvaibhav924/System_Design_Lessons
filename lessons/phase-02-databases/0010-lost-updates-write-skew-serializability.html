Phase 2.1 · Transactions (part 2)

Lost updates, write skew, and the three ways to get true serializability

Two users act at the same moment, each one's change looks valid, and together they break a rule. Snapshot isolation doesn't stop this. This lesson shows the bug and the three ways databases prevent it.

Reading time ~22 min Main source DDIA Ch. 7, "Preventing Lost Updates" to the end of the chapter Roadmap topics lost updates · write skew · phantoms · serializability · 2PL · SSI
What you'll be able to do Spot the two race conditions behind most "how did this happen?" data bugs: the lost update and write skew. Choose the right fix: an atomic update, a row lock, a constraint, or serializable isolation. Explain how the three serializability methods differ, and what each costs.

Lesson 0009 was about what a transaction can see while others write. This one is about two transactions writing at the same time.

01The lost update: read, change, write back

DDIA, "Preventing Lost Updates" — pp. 242–246

Any read-modify-write cycle can lose an update: read a value, compute a new one in your code, write it back. If two clients do this at once, the second write doesn't include the first change. The later write "clobbers" the earlier one. Kleppmann's examples include incrementing a counter or balance, adding an item to a list inside a JSON document, and two people saving the same wiki page.

The fixes, roughly from best to last resort:

FixHowWatch out
Atomic updateUPDATE counters SET value = value + 1 WHERE key = 'foo'. The database does the read and write as one step. "Usually the best choice" when the change can be written this way.ORMs make it "easy to accidentally" write the unsafe version instead.
Explicit lockSELECT … FOR UPDATE locks the rows you read until you commit. Use it when the logic is too complex for one UPDATE (Kleppmann's example: validating a move in a game)."It's easy to forget to add a necessary lock somewhere."
Automatic detectionThe database notices the lost update and aborts one transaction, which you retry. PostgreSQL's repeatable read does this, as do Oracle's serializable and SQL Server's snapshot isolation.MySQL/InnoDB's repeatable read does not.
Compare-and-setUPDATE … SET content = 'new' WHERE id = 1 AND content = 'old'. It writes only if nothing changed; if no row was updated, retry.Not safe if the database evaluates the WHERE against an old snapshot. "Check whether your database's compare-and-set operation is safe."
In your world

In Python ORMs the unsafe version looks innocent: job.retries += 1; job.save() is a read-modify-write in your process. Django's F("retries") + 1, or a plain SQL SET retries = retries + 1, is the atomic version. The same applies to anything counted per request: API quota used, tokens spent, examples labelled.

With replicas there's one more case. Locks and compare-and-set assume there's one up-to-date copy. Databases that accept writes on several replicas can't promise that, so they keep conflicting versions and merge them, or they fall back to last write wins, which "is prone to lost updates". Lesson 0015 covers this.

02Write skew: each change is fine, together they break the rule

DDIA, "Write Skew and Phantoms", Fig. 7-8 — pp. 246–249

Kleppmann's example: a hospital rule says at least one doctor must be on call. Alice and Bob are both on call and both feel ill. They press "go off call" at the same moment. Each transaction checks "are at least 2 on call?", sees yes, and updates its own row. Both commit, and nobody is on call.

This isn't a dirty write or a lost update, because the two transactions changed different rows. It's write skew: two transactions read the same data, then each updates a different part of it based on what it read. Run it under three database settings:

DDIA's Fig. 7-8 (the bug), its FOR UPDATE fix (p. 248), and Fig. 7-11 (how serializable snapshot isolation catches it). Step through each setting.

Write skew is not detected by PostgreSQL's or MySQL's repeatable read, Oracle's serializable or SQL Server's snapshot isolation. Atomic operations don't help because several rows are involved, and most databases can't express "at least one row must match" as a constraint. Your options: lock the rows you read (FOR UPDATE) or use true serializable isolation.

03Phantoms: when there's no row to lock

DDIA, "More examples of write skew" and "Phantoms causing write skew" — pp. 249–251

Once you know the pattern, you'll see it in many places. Kleppmann lists room booking (two people book the same slot), game moves (two pieces moved to the same square), claiming a username, and double-spending (two purchases each see enough balance). All of them follow the same three steps:

  1. A SELECT checks a condition ("no booking overlaps noon–1pm").
  2. The application decides based on the result.
  3. It writes, and the write changes the answer that step 1 would now give.

In the doctors case, you can lock the rows from step 1. But room booking checks that no rows exist, and you can't lock a row that isn't there. A write that changes another transaction's search result is called a phantom. Fixes:

  • A unique constraint, where the rule fits one (usernames). The second insert fails.
  • Materializing conflicts: create a table of rows that exist only to be locked, such as one row per room per 15-minute slot. It works, but it's "a last resort": error-prone, and concurrency control leaks into your data model.
  • Serializable isolation, which is "much preferable in most cases".
In your world

"Check the team's remaining GPU-hour or LLM-token budget, then start the job" is double-spending: two jobs launched at once both see enough budget. "Check the GPU node is free, then reserve it" is room booking. Both are phantom-style write skew. Use serializable isolation, a materialized "slot" row you lock, or an atomic UPDATE budget SET remaining = remaining - ? WHERE remaining >= ? that changes exactly one row.

04Serializability, and the three ways to get it

DDIA, "Serializability" — pp. 251–252

Kleppmann's complaint is that weak isolation levels are hard to understand and inconsistently implemented, you can't tell from your code whether it's safe, and concurrency bugs rarely show up in tests. Since the 1970s, researchers have given the same answer: "use serializable isolation!" It guarantees the result is the same as if the transactions ran one at a time, so code that's correct alone stays correct under concurrency. Why isn't it the default? Look at how it's built:

Method 1: actually run one at a time

DDIA, "Actual Serial Execution" — pp. 252–256

Use a single thread with no concurrency at all, and isolation is serializable by definition. Designers came round to this around 2007, once RAM got cheap enough to hold the working data and OLTP transactions turned out to be short. It's used by VoltDB, Datomic and Redis. The catch: you can't have back-and-forth with the client inside a transaction (the thread would sit idle waiting), so the whole transaction is sent at once as a stored procedure (Lua scripts in Redis). Limits: every transaction must be small and fast, because "it takes only one slow transaction to stall all transaction processing". Data should fit in memory. Throughput is one CPU core, unless you split the data into partitions, and cross-partition transactions are "vastly slower" (VoltDB: about 1,000 per second).

Method 2: two-phase locking (2PL)

DDIA, "Two-Phase Locking (2PL)" — pp. 257–261

This was the only widely used method for about 30 years. Readers take shared locks and writers take exclusive locks, and all of them are held until commit. Phase 1 acquires locks, phase 2 releases them all at the end. Unlike snapshot isolation, writers block readers and readers block writers. To stop phantoms, it also locks search conditions. In practice that's an approximation on an index (an index-range lock), or the whole table if no index fits. Used by MySQL/InnoDB's and SQL Server's serializable level. The cost: lower throughput, frequent deadlocks (the database aborts one transaction and you retry), and "quite unstable latencies… very slow at high percentiles". One long transaction can bring everything to a halt. Not to be confused with 2PC (two-phase commit), which is a different thing covered in Phase 5.

Method 3: serializable snapshot isolation (SSI)

DDIA, "Serializable Snapshot Isolation (SSI)", Figs. 7-10, 7-11 — pp. 261–266

This is snapshot isolation plus detection. Transactions run without blocking and read from their snapshot. The database tracks what each one read, and at commit it checks whether the transaction "acted on an outdated premise": did something it read change and get committed in the meantime? If so, the commit is aborted and you retry. That's what the simulator did to Bob. 2PL is pessimistic (wait in case of trouble); SSI is optimistic (proceed, check at the end). It's PostgreSQL's SERIALIZABLE level (since 9.1), and FoundationDB uses a similar method. Readers still never block writers, so latency is predictable. The cost is aborts: high contention or long read-write transactions mean many retries.

Interview red flag

"Wrap it in a transaction" is not an answer to a booking or balance race. The strong answer names the race (lost update or write skew), then picks a fix: an atomic conditional update, a unique constraint, SELECT … FOR UPDATE, or serializable isolation with retries. And it says that every one of these, plus the deadlocks and serialization failures, needs a retry loop in the application.

05The page in five lines

  1. Lost update: two read-modify-write cycles on the same row, so one change vanishes. Fix with atomic UPDATE x = x + 1, FOR UPDATE, automatic detection (not MySQL's repeatable read), or compare-and-set.
  2. Write skew: two transactions read the same rule, each updates a different row, and together they break it. Snapshot isolation doesn't catch it.
  3. Phantom: the check is "no such row exists", so there's nothing to lock. Use a unique constraint, materialized lock rows, or serializable isolation.
  4. Serializability methods: serial execution (Redis; small, fast transactions), 2PL (blocking, deadlocks, bad p99), SSI (optimistic, aborts on stale premises; PostgreSQL).
  5. Every fix needs the application to retry aborted transactions.
Optional: 30-second recall check 5 questions · click to open · not graded

Code does row = get(); row.count += 1; save(row) from many workers. What's the simplest safe fix?

An atomic update lets the database do the read and write as one step, so no increment is lost.

Two doctors each check "2 on call", each update their own row, and both commit. What is this?

They read the same data and wrote different rows. Snapshot isolation allows this; only serializability or explicit locks stop it.

Why can't SELECT … FOR UPDATE fix a double room booking on its own?

It's a phantom: the conflicting row doesn't exist yet. Materialize lock rows or use serializable isolation.

Which serializability method lets readers and writers proceed without blocking each other?

SSI reads from a snapshot without locks and aborts only transactions whose premise went stale. (Read committed isn't serializable.)

A service on PostgreSQL SERIALIZABLE sees occasional serialization failures. What should the code do?

SSI is optimistic: aborts are part of the design. The transaction did not commit and must be re-run.
