Phase 2.1 · Transactions (part 1)

Transactions: what ACID really promises, and what your database actually does

"It's an ACID database" sounds like a full guarantee. This lesson shows what each letter means, and why your database's default settings still let some concurrency bugs through.

Reading time ~20 min Main source DDIA Ch. 7 "Transactions", up to "Preventing Lost Updates" Roadmap topics transactions · ACID · isolation levels · MVCC
What you'll be able to do Explain each letter of ACID in one honest sentence. Name the problem that read committed and snapshot isolation each prevent (and the ones they don't). Explain how a database lets readers and writers work at the same time without blocking each other (MVCC).

01What a transaction is for

DDIA, Ch. 7 introduction — pp. 221–223

Kleppmann opens with a list of what goes wrong: the database or app crashes mid-write, the network cuts out, several clients overwrite each other, someone reads half-updated data. A transaction groups several reads and writes into one unit. Either all of it succeeds (commit) or none of it takes effect (abort / rollback), and then "the application can safely retry."

Transactions "are not a law of nature". They were invented to make application code simpler: the database handles a whole class of failures so your code doesn't have to. Kleppmann also dismisses both popular extremes: "transactions don't scale" and "serious apps need ACID" are "both pure hyperbole".

02ACID, one honest sentence per letter

DDIA, "The Meaning of ACID" — pp. 223–227

His warning comes first: "one database's implementation of ACID does not equal another's", and "ACID has unfortunately become mostly a marketing term."

"Consistency" means four different things

Kleppmann counts at least four: replicas agreeing eventually (replica consistency), consistent hashing, the C in CAP, which means linearizability (lesson 0004), and the C in ACID, which means your application's rules. In an interview, say which one you mean. And BASE ("basically available, soft state, eventual consistency"), the supposed opposite of ACID, is "even more vague". Its only sensible definition is "not ACID".

03Why you need more than one-row updates

DDIA, "Single-Object and Multi-Object Operations", Figs. 7-2, 7-3 — pp. 228–231

Kleppmann's example: an email app stores an unread_count next to the emails, so it doesn't have to count them on every page load. Now each new email means two writes: insert the email and increment the counter.

  • Without isolation, a reader can catch the moment between them: the inbox shows a new email while the counter still says 0.
  • Without atomicity, a crash between them leaves the two out of sync for good.

Almost every storage engine makes a single row or document update atomic and isolated, so you never see half a JSON document. Many also offer single-object tools such as an atomic increment and compare-and-set. These are useful, but Kleppmann calls it "misleading" when vendors market them as "lightweight transactions" or even "ACID". A transaction means grouping several objects. He also notes that a key-value store's multi-put "doesn't necessarily" have transaction semantics: some keys can succeed while others fail.

In your world

"Register model v7, mark it as production, demote v6" is three writes that must happen together. If a crash leaves two models marked production, or none, your serving layer has a real problem. That belongs in one transaction. The same applies to any denormalized counter or summary next to the raw data, such as "number of labelled examples" stored beside the examples.

04Aborts exist so you can retry, carefully

DDIA, "Handling errors and aborts" — pp. 231–232

"The whole point of aborts is to enable safe retries", yet popular ORMs such as Django and Rails ActiveRecord don't retry aborted transactions. The error just becomes an exception. Kleppmann's caveats on retrying are exactly lesson 0005 applied to databases:

  • The commit may have succeeded with only the acknowledgement lost, so a retry runs it twice unless you deduplicate (idempotency keys).
  • If the error is overload, retries make it worse: limit them and use exponential backoff.
  • Retry only temporary errors (deadlock, failover, isolation conflicts), not permanent ones (a constraint violation will fail again).
  • Side effects outside the database, such as sending an email, are not rolled back.

05Read committed: the default almost everywhere

DDIA, "Weak Isolation Levels" and "Read Committed", Figs. 7-4, 7-5 — pp. 233–237

Full serializable isolation costs performance, so databases offer weaker isolation levels. They are "much harder to understand", and the bugs they allow "have caused substantial loss of money". Kleppmann's point: "use an ACID database" doesn't save you, because those databases mostly default to weak isolation too.

The basic level is read committed, the default in PostgreSQL, Oracle and SQL Server. It makes two promises:

  • No dirty reads. You never see another transaction's uncommitted writes. Its changes appear all at once when it commits.
  • No dirty writes. You never overwrite another transaction's uncommitted write; you wait until it commits or aborts. Kleppmann's example: without this, two buyers of the same used car could end up with Bob recorded as the buyer and Alice receiving the invoice.

How it's built: writers take a row lock and hold it until commit. Readers don't lock (a long write would stall every reader). Instead the database keeps the old committed value and gives it to readers until the new one commits.

06Read skew, and the fix: snapshot isolation (MVCC)

DDIA, "Snapshot Isolation and Repeatable Read", Figs. 7-6, 7-7 — pp. 237–241

Read committed still allows this: Alice has $500 in each of two accounts. While $100 is being transferred between them, she reads one account before the transfer and the other after it, and sees $900 in total. Every value she read was committed, just at different moments. This is read skew, also called a non-repeatable read: reading the same row twice gives different answers.

For Alice a reload fixes it. For a backup or a long analytics query, it doesn't: a backup taken this way permanently contains half-applied transfers. The fix is snapshot isolation: each transaction reads from "a consistent snapshot of the database", meaning everything committed when the transaction started, and nothing later.

The implementation is multi-version concurrency control (MVCC). Every transaction gets an increasing ID. Rows are never updated in place: an update marks the old version deleted_by the writer and adds a new version created_by it. When you read, you see only versions created by transactions that had committed when you started. Step through it at each level:

DDIA's Figs. 7-6 and 7-7 combined. Alice is transaction 12, the transfer is transaction 13. Run all five steps under each level and watch both "what Alice sees" and which stored version (highlighted) her reads pick. Read uncommitted is shown only for contrast; few systems use it.
The property that makes it popular

With snapshot isolation, "readers never block writers, and writers never block readers". A three-hour report and a stream of live writes can run together without waiting on each other's locks. Old versions are removed later by a background garbage-collection process once no transaction can still see them. In PostgreSQL that process is VACUUM.

07The naming mess

DDIA, "Repeatable read and naming confusion" — p. 242

The SQL standard dates from before snapshot isolation existed, so databases ship it under borrowed names. PostgreSQL and MySQL call it repeatable read. Oracle calls it serializable, even though it isn't. IBM DB2 uses "repeatable read" for real serializability. Kleppmann's summary: "nobody really knows what repeatable read means." Always check what your database's level actually prevents.

In your world

Exporting a training set or a feature backfill from a live PostgreSQL database is exactly the "long analytics query" case. Under the default read committed, rows read early and late in the export reflect different moments, so joined tables can disagree. Run the export in one REPEATABLE READ (snapshot) transaction and the dataset matches a single point in time. The cost: a snapshot open for hours keeps old row versions from being cleaned up, so tables grow while it runs.

08The page in five lines

  1. A transaction makes a group of writes all-or-nothing, so the application can simply abort and retry. Retry with lesson 0005's care (idempotency, backoff, temporary errors only).
  2. ACID: A = abortability, C = your app's rules, I = isolation (rarely full serializability), D = disk + WAL and/or replicas. "ACID" alone tells you little.
  3. Read committed (common default): no dirty reads, no dirty writes. Still allows read skew.
  4. Snapshot isolation via MVCC: each transaction reads a frozen point in time, and readers and writers don't block each other. Use it for backups, exports and analytics.
  5. Level names are unreliable: "repeatable read" in PostgreSQL/MySQL means snapshot isolation, and Oracle's "serializable" isn't.
Optional: 30-second recall check 5 questions · click to open · not graded

Which ACID property is the application's responsibility rather than the database's?

The database can't know your invariants beyond constraints. C is a property of the application.

Under read committed, a report reads table A, then table B, while transfers run. What can go wrong?

That's read skew: every value was committed, just not at the same moment. Snapshot isolation fixes it.

How does MVCC let a long read run without blocking writers?

Writers add new versions instead of overwriting. The reader keeps seeing versions committed before it started.

PostgreSQL's "repeatable read" level is really which of these?

PostgreSQL and MySQL use the standard's name for their snapshot isolation level.

A transaction's commit times out on the client. Why is a blind retry risky?

Only the acknowledgement may have been lost. Without deduplication (an idempotency key), the retry applies the change again.
