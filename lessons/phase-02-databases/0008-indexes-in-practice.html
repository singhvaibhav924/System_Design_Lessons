Indexes in practice: what the database does with your WHERE clause

Lesson 0007 built the B-tree. This lesson covers how real queries use it: which index gets picked, why the order of columns matters, and why "we added an index" sometimes changes nothing.

Reading time ~20 min Main sources DDIA Ch. 3 "Other Indexing Structures" · Markus Winand, Use The Index, Luke · PostgreSQL docs Roadmap topics primary & secondary keys · composite & covering indexes · query planner · buffer pool
What you'll be able to do Look at a query and an index and say whether the index helps, and how much. Pick the column order of a multi-column index. Read the first line of an EXPLAIN plan and know what to check first when a query is slow.

The roadmap asks you to understand this path "rather than treating SQL as magic":

query → query planner → index → page cache / disk → result

We'll go through it in order, but start in the middle, with how a table and its indexes are laid out, because everything else depends on it.

01Where the rows live: heap files and clustered indexes

DDIA, "Other Indexing Structures" and "Storing values within the index" — pp. 85–87

The primary key identifies one row. A secondary index (anything you add with CREATE INDEX) is on some other column, so its keys don't have to be unique: many rows can share a user_id. Both are usually B-trees. What differs between databases is what the index entry points to:

Heap file + indexesClustered index
Where full rows liveA separate heap file, in no particular order Inside the primary-key B-tree's leaf pages
Secondary index storesA pointer to the row's location in the heapThe row's primary key, so a second lookup in the primary-key tree follows
ExamplePostgreSQLMySQL's InnoDB ("the primary key of a table is always a clustered index")

Kleppmann's point is that the heap avoids duplicating data across many indexes, while a clustered index saves the extra hop on reads. Either way, a lookup through a secondary index usually ends with a second step to fetch the row. That step turns out to be where most of the time goes.

02An index lookup is three steps, and only one is cheap for sure

Winand, Use The Index, Luke, "Slow Indexes" — use-the-index-luke.com

DDIA doesn't cover this part, so I'm using Markus Winand's Use The Index, Luke, the standard practical guide. He splits every index lookup into:

  1. Walk down the tree to the first matching entry. This is the 3–4 page reads from lesson 0007. "The only step that has an upper bound".
  2. Walk along the leaf pages while entries still match. With 50,000 matches, that's a lot of leaves.
  3. Fetch each matching row from the table. The rows are scattered across the heap, so each match can cost its own page read.
The myth to drop

"It uses an index, so it's fast" is false. Step 1 is always cheap; steps 2 and 3 grow with the number of matching rows. An index helps most when it narrows the result down to few rows. For a query matching half the table, reading the whole table front to back is often faster than thousands of scattered row fetches, and the planner (section 05) knows this.

03Multi-column indexes: the order of columns decides everything

DDIA, "Multi-column indexes" — p. 87; Winand, "Concatenated Keys" and "Greater, Less and Between"

An index on (last_name, first_name) is a phone book. It's sorted by last name, and by first name only within each last name. So it's useful for "all the Smiths" and for "John Smith", but, in Kleppmann's words, "useless if you want to find all the people with a particular first name." The same entries are spread all over the book.

Two rules follow:

  • Leftmost prefix. An index on (a, b, c) helps queries on a, on a + b, or on a + b + c, but not on b alone. Winand: the column order "has great impact on its usability", so choose it so that the index "can be used as often as possible".
  • "Index for equality first, then for ranges." If a query has user_id = 3 and day BETWEEN 2 AND 4, put user_id first. Then the matches sit next to each other in the index. With day first, the index narrows only by day, and every user in that date range has to be read and checked.
24 index entries for 4 users × 6 days, shown in index order (each cell is first column · second column). Switch the index between (user_id, day) and (day, user_id) and compare the queries. "Read" means the database had to look at the entry.
In your world

The classic feature-table query is "the latest features for this entity before time T": WHERE entity_id = ? AND event_ts <= ?. That needs an index on (entity_id, event_ts), with equality first and the range second. Reversed, every lookup scans everyone's events in the time range. A bonus: a B-tree returns entries in index order, so the same index also serves ORDER BY event_ts DESC LIMIT 1 without a separate sort.

04Covering indexes: skip the table entirely

DDIA, "covering index" — pp. 86–87; PostgreSQL docs, "Index-Only Scans and Covering Indexes"

Step 3 (fetching rows) disappears if the index already contains every column the query needs. DDIA calls that a covering index: it stores some extra columns so that "some queries [can] be answered by using the index alone". In PostgreSQL you add the extra columns with INCLUDE:

-- query:  SELECT score FROM predictions WHERE request_id = ?;
CREATE INDEX ON predictions (request_id) INCLUDE (score);

The plan then shows an Index Only Scan. There's a PostgreSQL detail: it may still check the table to confirm a row is visible to your transaction, so the gain is largest on tables that rarely change. The cost is the usual one for duplicated data: a bigger index and slower writes. The docs say to use included columns "conservatively".

05The query planner: an estimator, not a rule-follower

PostgreSQL docs, "Using EXPLAIN" and "Statistics Used by the Planner"

SQL says what you want, and the query planner decides how to get it. It considers several plans, estimates each one's cost from statistics about your data (row counts, common values, value distributions), and picks the cheapest. The PostgreSQL docs show the same query getting three different plans as the condition becomes more selective, on a 10,000-row table with an index on unique1:

ConditionRows estimatedPlan chosenWhy
unique1 < 70007,000Seq Scan (whole table)Most rows match, so reading everything in order is cheapest
unique1 < 100100Bitmap scanUse the index to collect row locations, then read those pages in disk order
unique1 = 421Index ScanOne row: walk the tree, fetch it

That's the "it ignored my index!" mystery: often the planner was right. When it's wrong, the usual cause is a bad row estimate. EXPLAIN shows the plan and its estimates. EXPLAIN ANALYZE actually runs the query and adds the real numbers, and the docs say what to check first: "whether the estimated row counts are reasonably close to reality."

EXPLAIN ANALYZE SELECT * FROM tenk1 WHERE ten < 7;
 Seq Scan on tenk1  (cost=0.00..470.00 rows=7000 width=244) (actual time=0.030..1.995 rows=7000.00 loops=1)
                                       ^^^^^^^^^ estimate                               ^^^^^^^^^^^^ reality
Common reasons the index isn't used

Stale statistics. They're refreshed by ANALYZE, which normally runs automatically in the background. After a big bulk load, the planner may still think the table is tiny. Correlated columns. The planner "normally assumes that multiple conditions are independent", which can underestimate results badly (the docs show a city/state pair under-estimated a hundredfold). A function wrapped around the column. WHERE UPPER(name) = 'SMITH' can't use an index on name, because the index holds name, not UPPER(name). The fix is an index on the exact expression (Winand). The same applies to LIKE '%term': a B-tree is sorted from the first character, so a leading wildcard gives it nothing to search by.

06The buffer pool: why the second run is faster

PostgreSQL docs, shared_buffers; DDIA, "Keeping everything in memory" — p. 89

Databases don't read rows; they read pages (8 KB in PostgreSQL, 16 KB by default in InnoDB). Recently used pages are kept in RAM in the buffer pool (shared_buffers in PostgreSQL). For a dedicated server the docs suggest about 25% of RAM to start, "because PostgreSQL also relies on the operating system cache", which holds a second copy of recently read file pages. The Buffers: shared hit=345 line in EXPLAIN ANALYZE output means all 345 pages came from memory.

Two practical consequences:

  • The top levels of every busy B-tree are always in memory, so a "4-level" lookup usually costs only one or two real disk reads.
  • Benchmark warm and cold separately. The first run of a query reads from disk and later runs hit the cache. Kleppmann makes a related point: in-memory databases aren't fast mainly because they skip disk reads (a disk-based engine with enough RAM rarely reads disk either), but because they avoid converting data into an on-disk format.

07Indexes beyond the B-tree, briefly

DDIA, "Multi-column indexes" and "Full-text search and fuzzy indexes" — pp. 87–88
  • Multi-dimensional: "restaurants inside this map rectangle" needs latitude and longitude ranges at once, which a B-tree can't do (it narrows only one range). Spatial indexes such as R-trees (PostGIS) handle it. Phase 11 · geospatial
  • Full-text: maps each word to the list of documents containing it, with fuzzy matching for typos (Lucene, Elasticsearch). Phase 11 · search
  • Vector indexes: "nearest embeddings to this one", the core of semantic search and RAG. Not in DDIA (2017). Phase 13 · LLM systems

08The page in five lines

  1. A secondary-index lookup = walk the tree (cheap), walk the matching leaves, then fetch each row from the table (heap or clustered primary key). The last two grow with the number of matches.
  2. Indexes help most when they narrow to few rows. For broad queries, a full sequential scan can win.
  3. Multi-column index: leftmost prefix only, and equality columns first, range column last.
  4. A covering index holds every column the query needs, so the row fetch disappears (Index Only Scan), at the cost of size and write speed.
  5. The planner picks plans from statistics. EXPLAIN ANALYZE: compare estimated vs actual rows first. Remember the buffer pool when timing queries.
Optional: 30-second recall check 5 questions · click to open · not graded

There's an index on (user_id, created_at). Which query can't use it efficiently?

Leftmost prefix: the index is sorted by user_id first, so dates alone are scattered across every user's section.

A query has tenant_id = ? and ts BETWEEN ? AND ?. Which column order is best?

With the equality column first, all matches sit in one contiguous slice. With the range first, the index narrows only by time.

A query matches 60% of a large table, and the planner chooses a sequential scan over the index. Why?

Index lookups pay one table fetch per match. For broad queries, scanning the table front to back is cheaper.

What does a covering index remove from a lookup?

If the index holds every column the query needs, the database answers from the index alone (an Index Only Scan).

In EXPLAIN ANALYZE output, what should you check first?

Bad row estimates are the usual root cause of bad plans. Cost units are arbitrary and don't map to milliseconds.
