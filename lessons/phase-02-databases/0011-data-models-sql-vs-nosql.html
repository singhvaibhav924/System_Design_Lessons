Phase 2.1 · Data models

Tables, documents or graphs: picking a data model by its relationships

"SQL or NoSQL?" is the wrong question. The useful question is how the pieces of your data relate to each other, because each data model makes some relationships easy and others painful.

Reading time ~20 min Main sources DDIA Ch. 2 · Chip Huyen, DMLS Ch. 3 "Data Models" · Alex Xu Ch. 1 Roadmap topics schema design · normalization · denormalization · primary & foreign keys · SQL vs NoSQL
What you'll be able to do Look at a dataset and say whether it's mostly a tree (documents fit), a web of references (relational fits) or relationships first (a graph fits). Explain what normalizing and denormalizing each cost, and answer "SQL or NoSQL?" with reasons instead of fashion.

01A data model decides which questions are easy

DDIA, Ch. 2 introduction — pp. 27–28; DMLS, "Data Models" — pp. 58–59

Kleppmann calls data models "perhaps the most important part of developing software", because they shape "how we think about the problem". Chip Huyen's example: describe a car by make, model, year and price, and it's easy for buyers. Describe the same car by owner, licence plate and address history, and it's easy for the police. Same car, different questions made easy.

Every model "embodies assumptions about how it is going to be used". So the real question is always: what are the relationships in my data, and which queries will I run most? We'll take the three main models in turn.

02Relational: store each fact once, join when reading

DDIA, "Many-to-One and Many-to-Many Relationships" — pp. 33–34; DMLS Tables 3-2 to 3-4 — pp. 59–61

The relational model (Codd, 1970) puts data in tables of rows. Its key habit is normalization: each human-meaningful fact is stored once, and everything else refers to it by ID. In Huyen's example, "Banana Press, UK" is repeated on three book rows. Move it to a publisher table and give each book a publisher_id (a foreign key). Kleppmann's rule of thumb for spotting a non-normalized schema: "if you're duplicating values that could be stored in just one place". You don't need the formal normal forms (1NF, 2NF…); he calls their distinctions "of little practical interest".

Why bother? An ID "never needs to change", but anything meaningful to humans does: names get rebranded, cities renamed, labels translated. Duplicated copies all have to be updated, which means more writes and the risk that some copies are missed. The price, in Huyen's words: data is "spread across multiple relations", and joining it back "can be expensive for large tables". Denormalization is the deliberate reverse: copy data in to make reads cheaper, and accept the job of keeping the copies in sync (the unread-counter example in lesson 0009).

03Documents: great for trees, awkward for references

DDIA, "The Object-Relational Mismatch" and "Relational Versus Document Databases Today" — pp. 29–32, 38–41

Kleppmann's example is a LinkedIn profile: one user with many jobs, many schools and several contact links. That's a tree of one-to-many relationships, usually loaded all at once. Relationally it's spread over four tables and needs "a messy multi-way join". As one JSON document (MongoDB, CouchDB) it's one read. That's the locality advantage, plus less translation between your code's objects and the database.

The trouble starts with references. Is "Microsoft" just a string in the profile, or a company entity with its own page and logo? Do users write recommendations for other users, showing the recommender's current photo? Those are many-to-one and many-to-many relationships, and "data has a tendency of becoming more interconnected as features are added". Document databases have weak join support, so you either denormalize (and keep copies in sync yourself) or join in application code with several queries, which is "usually slower". Kleppmann's summary: for highly interconnected data "the document model is awkward, the relational model is acceptable, and graph models… are the most natural."

Two more practical limits: the database usually loads and rewrites the whole document even if you change one field, so keep documents small. And you can't easily point to "the second job in user 251's list".

"Schemaless" is really schema-on-read

DDIA, "Schema flexibility in the document model" — pp. 39–41

The code reading the data always assumes some structure, so "there is an implicit schema, but it is not enforced by the database". Kleppmann compares it to programming languages: schema-on-write (relational: the database checks every row) is like static typing; schema-on-read (documents: readers cope) is like dynamic typing. Schema-on-read helps when records really differ, or when an outside system controls the structure. When every record should look the same, a schema documents and enforces it. Changing a schema means either a migration (ALTER TABLE is usually fast, but backfilling every row with UPDATE is slow anywhere) or handling old and new shapes in the code that reads them.

In your world

Huyen tells of a schema change that replaced missing ages with 0, after which "their ML model thought the transactions were made by people 0 years old" (DMLS p. 66). Schema changes are a classic way for silent garbage to reach a model. Whoever owns the schema (database or reader) must also decide what "missing" looks like.

04Graphs: when the relationships are the data

DDIA, "Graph-Like Data Models" — pp. 49–51; DMLS, "Graph model" — pp. 65–66

When many-to-many relationships dominate, model the data as vertices (things) and edges (relationships): social networks, the web's link graph, road networks. Facebook stores people, places, events and comments as one graph of different vertex and edge types. Huyen's example query is "everyone born in the USA", where a person may be linked to a city, which is in a state, which is in the country. The number of hops varies, so there's "no easy way" to write it in SQL, but in a graph it's a traversal. Graph databases include Neo4j (query language Cypher). You won't need graph query languages for interviews; knowing when a graph fits is enough.

05This debate is fifty years old, and the models are converging

DDIA, "Are Document Databases Repeating History?" and "Convergence" — pp. 36–42

IBM's IMS (1968, built for Apollo stock-keeping) stored data as nested trees, much like JSON documents, and had the same problem with many-to-many relationships. The relational model won partly because of the query optimizer (lesson 0008). You describe what you want, the database picks the access path, and adding an index doesn't require rewriting queries. "You only need to build a query optimizer once."

Today the camps are merging. PostgreSQL and MySQL store and index JSON, and document databases have added join-like features. Kleppmann calls a hybrid "a good route", and Huyen notes it's "common to use both models for different tasks in the same database". Using several kinds of store in one system, each for what it's good at, is called polyglot persistence.

06"SQL or NoSQL?" in an interview

Xu, Ch. 1, "Which databases to use?" — p. 8; DDIA, "The Birth of NoSQL" — p. 29

"NoSQL" doesn't name a technology. It started as "a catchy Twitter hashtag for a meetup" in 2009 and was later reinterpreted as "Not Only SQL". Xu splits it into four families, which are really different data models:

FamilyShapeExamplesFits
Key-valueKey → opaque valueRedis, DynamoDBLookups by ID: sessions, caches, online feature lookups
DocumentKey → nested JSONMongoDB, CouchDBSelf-contained trees loaded whole: profiles, configs, catalogue items
Wide-columnRows of many columns, grouped by partition key, LSM storage (0007)Cassandra, HBaseHuge write volumes read by key and time: events, logs, time series
GraphVertices + edgesNeo4jRelationship-heavy queries: social, fraud rings, knowledge graphs

Xu's default: "for most developers, relational databases are the best option", and look further when you need super-low latency, have unstructured or non-relational data, only store and fetch serialized blobs, or have "a massive amount of data". The strong interview answer adds reasons:

  • Relationships: a tree favours documents, references favour relational, relationship-heavy data favours a graph.
  • Access pattern: mostly lookups by key, or ad-hoc queries and joins?
  • Correctness: do you need multi-row transactions (lessons 0009–0010)? Many NoSQL stores don't offer them.
  • Scale: does the write volume or data size really outgrow one well-indexed relational node plus replicas? Phase 2 · replication & sharding next
In your world

A typical ML platform is already polyglot. Experiments, runs and the model registry sit in PostgreSQL: many references, transactions needed. Run configs and hyperparameters are a natural JSON column inside it, since their shape varies by model. Prediction and event logs go to a wide-column or log store: huge append volume, read by key and time. Online features go to a key-value store, and embeddings to a vector index Phase 13.

07The page in five lines

  1. Choose a data model by its relationships and your most common queries, not by fashion.
  2. Normalize: each fact once, referenced by ID. Cheap, safe updates; reads need joins. Denormalize: copies for fast reads; you keep them in sync.
  3. Documents suit self-contained trees (locality, one read). Many-to-many forces app-side joins or duplication. Whole-document rewrites, so keep them small.
  4. "Schemaless" = schema-on-read: the schema still exists, in every reader. Relational = schema-on-write.
  5. "NoSQL" = key-value, document, wide-column and graph. Default to relational, and name the concrete reason when you don't.
Optional: 30-second recall check 5 questions · click to open · not graded

Why store a region_id instead of the text "Greater Seattle Area" in every profile?

Normalization: the human-meaningful value is stored once, so a rename is one update instead of many.

Which data fits a document model best?

A self-contained tree of one-to-many relationships, read all at once, is the document model's sweet spot.

What does "schemaless" really mean for a document database?

Schema-on-read: the structure is implicit, and every piece of code that reads the data must handle every shape it might find.

You denormalize a publisher's name into every book row. What new job do you take on?

Denormalized copies make reads cheap, but you must keep them in sync, ideally in one transaction.

An interviewer asks "SQL or NoSQL?" for user accounts with payments. What's the strongest start?

Payments need transactions and accounts reference many things. Relational by default, with the reason stated.
