Phase 2.2 · Database internals (part 1)

How a database finds your row: logs, LSM-trees and B-trees

Almost every database you will use stores data in one of two ways. Each one is fast at something different, and that difference explains which database fits which job.

Reading time ~20 min Main source DDIA Ch. 3 "Data Structures That Power Your Database" · Alex Xu Ch. 6 Roadmap topics indexes · SSTables · LSM-trees · compaction · B-trees · pages · WAL · write amplification
What you'll be able to do Explain, step by step, what happens on disk when a database writes and reads a key in the two big designs: LSM-trees (Cassandra, RocksDB, HBase) and B-trees (PostgreSQL, MySQL and almost every relational database). Then say which one you'd pick for a write-heavy job and which for a read-heavy one, and what each choice costs.

Kleppmann's reason for caring: you will probably never write a storage engine, "but you do need to select a storage engine that is appropriate for your application", and tuning one needs "a rough idea of what the storage engine is doing under the hood." When an interviewer asks "why Cassandra here and not Postgres?", this lesson is the answer.

01The simplest database, and the trade-off every index makes

DDIA, Ch. 3, "Data Structures That Power Your Database" — pp. 70–71

Kleppmann opens with a complete key-value database written as two shell functions:

db_set () { echo "$1,$2" >> database; }                                  # append a line
db_get () { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }   # newest match wins

Every write appends a line to the end of a file. Updating a key doesn't overwrite anything; it just adds a newer line, and a read takes the last match. A file you only ever add to is called a log (here that means "append-only sequence of records", not application logs). Appending is about the cheapest write a disk can do, so db_set is fast.

db_get is terrible: it reads the whole file on every lookup, so double the data and every read takes twice as long. The fix is an index, an extra structure kept on the side that points to where each piece of data lives. It brings the central trade-off of this whole chapter:

The index trade-off

"Well-chosen indexes speed up read queries, but every index slows down writes", because each index must also be updated on every write. That's why databases don't index everything automatically. You choose indexes based on the queries you actually run.

Everything below is a different answer to one question: how do you keep the index up to date without losing the fast appending?

02Step 1: a hash map pointing into the log

DDIA, "Hash Indexes", Figs. 3-1 to 3-3 — pp. 72–75

The simplest index: keep a dictionary in memory that maps every key to its byte offset in the log. A write appends to the file and updates the dictionary. A read looks up the offset and jumps straight there. This is essentially Bitcask, the default engine in the Riak database, and it's fast, as long as all the keys fit in RAM. Kleppmann's example of a good fit is a play counter per cat video: few distinct keys, many updates each.

Two pieces of housekeeping make it practical, and both come back in every log-based design:

  • Segments and compaction. The log is cut into segments. In the background, old segments are merged and compacted: duplicate keys are thrown away, keeping only the newest value. The merged result goes to a new file, and the old files are deleted only after the switch, so reads and writes carry on during the merge.
  • Tombstones. You can't delete from an append-only file, so a delete appends a special "this key is deleted" record called a tombstone. Compaction later drops the key's old values.

Kleppmann's case for appending over editing in place: sequential writes are much faster than random writes, and crash recovery is simple because a file that's never edited can't be left half-overwritten.

The two limits that push us to the next design: the keys must fit in memory, and range queries are slow. To fetch every key between kitty00000 and kitty99999 you'd have to look up each key one by one, because a hash map keeps no order.

03Step 2: keep each file sorted (SSTables and the LSM-tree)

DDIA, "SSTables and LSM-Trees", Figs. 3-4, 3-5 — pp. 76–79

One change fixes both limits: require every segment file to be sorted by key, with each key at most once. That file is a Sorted String Table (SSTable). Sorting buys three things:

  1. Merging is cheap, even for files bigger than memory: read the files side by side and always copy out the smallest key, the same idea as merge sort. If a key is in several files, the newest file wins.
  2. The in-memory index can be sparse. Store the offset of only one key every few kilobytes. To find handiwork, jump to handbag (the nearest key before it) and scan forward a few KB.
  3. Blocks compress well, which saves disk space and disk bandwidth.

But writes arrive in random order. How do they end up sorted on disk without random writes? The trick is to sort in memory first:

Xu, Ch. 6, "Write path" and "Read path" (Cassandra) — pp. 105–106
  1. 1Append the write to a log on disk Unsorted and append-only, so it's cheap. Its only job is to rebuild memory after a crash. Xu calls it the commit log.
  2. 2Insert it into the memtable An in-memory structure that keeps keys sorted (a balanced tree such as a red-black tree). Writes are acknowledged now.
  3. 3When the memtable is full, flush it as a new SSTable "Typically a few megabytes." It's already sorted, so this is one sequential write. The matching log can then be thrown away.
  4. 4Compact in the background Merge SSTables, keep the newest value per key, drop tombstoned keys.

A read checks the memtable, then the newest SSTable, then the next older one, and so on. This design (memtable plus a cascade of SSTables merged in the background) is the Log-Structured Merge-tree, or LSM-tree. LevelDB and RocksDB use it, and so do Cassandra and HBase. Lucene, the search library under Elasticsearch, keeps its word index in similar sorted files.

Try it. Write a few keys, watch the memtable fill and flush, read a key that lives in an old file, then compact:

Things to try: (1) press "+ 5 random writes" a few times, then read a key: the read walks newest → oldest. (2) Delete a key and read it: the tombstone answers "deleted" before older files are reached. (3) Press "Crash & restart": memory is wiped and rebuilt from the log. (4) Watch "write amplification" climb as you compact: the same records are rewritten to disk again and again.

Two refinements matter in interviews:

  • Bloom filters. Reading a key that doesn't exist is the worst case: you check every SSTable before giving up. So each SSTable keeps a Bloom filter, which can say "definitely not in this file" without touching the disk. Its "maybe" is occasionally wrong, which only costs one wasted read. (The simulator's filter is perfect, to keep it simple.)
  • Compaction strategy. Size-tiered merges smaller, newer files into bigger, older ones (HBase). Leveled splits the key range into small files arranged in levels, so compaction is more gradual and uses less disk space (LevelDB, RocksDB; Cassandra offers both).

04The other design: B-trees, a tree of fixed-size pages

DDIA, "B-Trees", Figs. 3-6, 3-7 — pp. 79–81

Logs are gaining ground, but the most widely used index is the B-tree. It was introduced in 1970, called "ubiquitous" less than ten years later, and it is still "the standard index implementation in almost all relational databases". Like an SSTable, it keeps keys sorted, so range queries are fast. Otherwise the philosophy is opposite:

LSM-treeB-tree
Unit on diskVariable-size segment files, megabytes eachFixed-size pages, traditionally 4 KB, matching how disks are laid out
How a write landsAppended; files are never changed, only replacedOverwrites the page in place
Where a key livesPossibly in several files (old versions until compaction)In exactly one place

Pages refer to each other by their location on disk, like pointers, which builds a tree. Each page covers a range of keys and points to child pages for smaller sub-ranges, down to leaf pages that hold the keys themselves. Follow DDIA's example of looking up key 251:

Drag the slider to look up other keys. "ref" is a page reference: the location of a child page on disk. Real pages hold hundreds of references, not five.

The number of children per page is the branching factor, and in practice it's "several hundred". Because each level multiplies capacity by that much, the tree stays very shallow: "most databases can fit into a B-tree that is three or four levels deep". A lookup reads only that many pages, and the top levels are usually already cached in memory.

The defaults are DDIA's numbers: 4 levels, 4 KB pages, branching factor 500 → 256 TB.

Writes. To update a key, find its leaf page, change it and write the page back. To insert into a full page, split it into two half-full pages and update the parent to point to both. This keeps the tree balanced, at depth O(log n), however much data you add.

05Overwriting in place is dangerous: the write-ahead log

DDIA, "Making B-trees reliable" — pp. 82–83

A page split writes three pages: the two halves and the parent. If the machine crashes after writing only some of them, the tree is corrupted. For example, a page may be left that no parent points to. The standard fix is a write-ahead log (WAL), also called the redo log: an append-only file where "every B-tree modification must be written before it can be applied to the pages of the tree itself." After a crash, the database replays the log and repairs the tree.

Notice the pattern

Both designs end up with an append-only log in front of everything else. The LSM-tree uses it to rebuild the memtable. The B-tree uses it to repair half-finished page writes. Write it to a log first, then do the real work is the basic crash-safety move. You'll meet it again as Kafka's log, replication logs and event sourcing.

Overwriting in place has one more cost. If several threads change the tree at once, one could see it half-updated, so B-trees protect pages with latches. LSM-trees avoid most of this: they merge in the background and swap in the new files all at once.

06LSM vs B-tree: what each one costs you

DDIA, "Comparing B-Trees and LSM-Trees" — pp. 83–85

The rule of thumb: "LSM-trees are typically faster for writes, whereas B-trees are thought to be faster for reads". LSM reads are slower because they may check several structures. Kleppmann immediately adds that benchmarks are "often inconclusive and sensitive to details of the workload". The reasons behind the rule:

Write amplification is "one write to the database resulting in multiple writes to the disk over the course of the database's lifetime". Both designs have it. A B-tree writes everything at least twice (WAL, then the page), and rewrites a whole 4 KB page even when only a few bytes changed. An LSM-tree rewrites data on every compaction. On a write-heavy system, disk bandwidth is the limit, so fewer bytes written means more writes per second. It matters on SSDs too, which wear out after a limited number of overwrites.

LSM-treeB-tree
Write throughputUsually higher: sequential writes, often lower write amplificationLower: several page overwrites per write
ReadsMay check memtable + several SSTables (Bloom filters help)One path of 3–4 pages
Disk spaceSmaller: compresses well, compaction removes gapsSome space lost to half-empty pages after splits
Tail latencyCompaction competes for disk, so p99 can spikeMore predictable
TransactionsSame key may exist in several filesEach key in exactly one place, so locks on key ranges attach directly to the tree
Typical enginesRocksDB, LevelDB, Cassandra, HBasePostgreSQL, MySQL (InnoDB), most relational databases
The failure that bites LSM systems in production

Disk bandwidth is shared between new writes and background compaction. If writes come in faster than compaction can merge them, "the number of unmerged segments on disk keeps growing until you run out of disk space", and reads slow down because they must check more files. Kleppmann warns that these engines usually don't slow down incoming writes to protect themselves, "so you need explicit monitoring to detect this situation." This is the p99 story from lesson 0002 again: the average looks fine while the tail suffers.

The B-tree's "one place per key" property is why it suits databases with strong transactions. Kleppmann's conclusion: there is "no quick and easy rule", so test with your own workload, but B-trees aren't going away, and new datastores are increasingly log-structured.

In your world

Write-heavy, key-based data such as prediction logs, click events and per-user features updated all day suits LSM-based stores. That's why Cassandra-style databases show up as online stores for features and event data. Stream processors use the same engine to hold their state: Flink and Kafka Streams both keep it in RocksDB. Expect occasional slow reads during heavy compaction.

Read-heavy data with relations and transactions, such as your experiment tracker, model registry or user accounts, usually lives in PostgreSQL or MySQL, which means B-trees. If someone proposes an LSM store for a workload that's 99% reads and needs transactions, ask why.

07The page in five lines

  1. An index is extra data kept on the side so reads don't scan everything. It speeds up reads and slows down every write.
  2. LSM-tree: log the write, put it in a sorted memtable, flush to immutable sorted files (SSTables), merge them in the background (compaction). Reads go newest → oldest, and Bloom filters skip files that can't contain the key.
  3. B-tree: a shallow tree of fixed-size pages (3–4 levels, branching factor in the hundreds), updated in place, with page splits on insert.
  4. Both put an append-only log first (commit log / write-ahead log) for crash safety.
  5. LSM: higher write throughput and smaller files, but compaction can hurt p99 and fall behind. B-tree: faster and more predictable reads, a natural fit for transactions.
Optional: 30-second recall check 5 questions · click to open · not graded

Why doesn't a database simply index every column by default?

Indexes speed up reads, but each one adds work to every write. You choose them based on the queries you actually run.

In an LSM-tree, a write has just been acknowledged. Where does it live right now?

The log on disk makes it crash-safe; the sorted memtable makes it fast to read. It reaches an SSTable only when the memtable is flushed.

What does a Bloom filter save an LSM-tree from?

It answers "definitely not here" from memory, so a read skips that SSTable. It matters most for keys that don't exist anywhere.

Why can a B-tree with 4 KB pages index hundreds of terabytes in only four levels?

Capacity grows as branching factor to the power of levels: 500⁴ pages × 4 KB ≈ 256 TB.

An LSM-based store's p99 read latency climbs every afternoon while its write rate peaks. What's the likely cause?

Compaction and new writes share the same disk. If compaction falls behind, reads must also check more SSTables.
