Phase 2.3 · Replication (part 2)

Replication lag: when your own edit disappears and time runs backwards

Reading from asynchronous followers is how you scale reads. It also means users sometimes see the past. This lesson covers the three anomalies they'll notice and the guarantee that fixes each one.

Reading time ~15 min Main source DDIA Ch. 5 "Problems with Replication Lag" Roadmap topics replication lag · eventual consistency · read-your-writes · monotonic reads · consistent prefix
What you'll be able to do Name the anomaly behind a "my change vanished" or "it appeared then disappeared" bug, and pick the matching fix: read-your-writes, monotonic reads or consistent prefix reads. You'll also be able to say precisely what "eventually consistent" does and doesn't promise.

01"Eventually" has no deadline

DDIA, "Problems with Replication Lag" — pp. 161–162

The read-scaling recipe from lesson 0013 (many followers, reads spread across them) "only realistically works with asynchronous replication". So a follower may be behind, and the same query on the leader and on a follower can return different answers. If writes stopped, the followers would catch up. That's eventual consistency.

Kleppmann's point is that "eventually" is "deliberately vague: in general, there is no limit to how far a replica can fall behind." Normally the replication lag is a fraction of a second. Near capacity or during network trouble it becomes "several seconds or even minutes", and then users notice. Eventual consistency isn't just a NoSQL thing either: an asynchronously replicated PostgreSQL or MySQL behaves exactly the same way.

Three anomalies show up, each with its own fix. Step through each one, then tick its fix and replay:

DDIA's Figures 5-3 (read your own writes), 5-4 (monotonic reads) and 5-5 (consistent prefix reads). Each follower's lag is fixed so the timing is repeatable.

02Read-your-writes: "I posted it, where did it go?"

DDIA, "Reading Your Own Writes", Fig. 5-3 — pp. 162–164

A user submits something, which goes to the leader, then views it, which is read from a lagging follower. "To the user, it looks as though the data they submitted was lost." Read-after-write (read-your-writes) consistency guarantees that users always see their own updates after a reload. It promises nothing about other users' updates. Ways to get it:

  • Read anything the user may have changed from the leader. For example, your own profile comes from the leader and other people's profiles from followers.
  • If almost everything is editable, use a time window: read from the leader for a minute after the user's last write, or avoid followers more than a minute behind.
  • Remember the position of the user's last write and only read from a replica that has reached it, or wait until it has. A logical position such as the log sequence number is safer than a wall-clock timestamp, which brings back the clock problems from lesson 0006.

Two complications: multiple datacenters (reads that need the leader must be sent to the leader's datacenter) and multiple devices. What you saved on your laptop should appear on your phone, but the phone doesn't know about the laptop's last write, so that information has to be stored centrally.

In your world

A deploy script writes "model v7 is now production" to the registry's primary database. Serving pods then poll the registry, via a read replica, to decide which model to load. For a few seconds, or minutes if the replica is struggling, some pods load v7 and some keep v6. If that matters, read the decision from the leader or pass the version explicitly in the deploy. Don't rely on a replica to tell you what just changed.

03Monotonic reads: "it was there a second ago"

DDIA, "Monotonic Reads", Fig. 5-4 — pp. 164–165

A user refreshes twice and each request goes to a random replica: first a fresh one, then a stale one. A comment that appeared now disappears, so time seems to run backwards, which is "very confusing". Monotonic reads guarantee that one user's successive reads never go back in time. They may still see old data, just never older than what they've already seen. It sits between strong and eventual consistency.

The fix: each user always reads from the same replica, chosen for example by a hash of their user ID instead of at random. If that replica fails, the user has to be moved to another one. This is the same "sticky" routing idea as session affinity in lesson 0001.

04Consistent prefix reads: the answer before the question

DDIA, "Consistent Prefix Reads", Fig. 5-5 — pp. 165–167

Mr. Poons asks "How far into the future can you see?" and Mrs. Cake replies "About ten seconds usually." If the two messages are stored in different partitions that replicate at different speeds, an observer can see the answer before the question. Consistent prefix reads guarantee that writes made in some order are read in that order.

With one leader applying everything in one order this can't happen. It's a problem in sharded databases, where partitions are independent and there's no global order. Fixes: put causally related writes (one conversation, one user's events) in the same partition, or track "happened-before" relationships explicitly 0015 · version vectors.

05Design for lag measured in minutes

DDIA, "Solutions for Replication Lag" — p. 167

Kleppmann's test: imagine the lag grows "to several minutes or even hours". If the answer is "no problem", fine. If not, design for a stronger guarantee, because "pretending that replication is synchronous when in fact it is asynchronous is a recipe for problems down the line." Fixing it in application code is "complex and easy to get wrong", which is why databases that offer stronger guarantees (transactions, and later linearizability) exist.

Interview red flag

"Reads go to replicas" with no follow-up. The strong answer adds: "replicas are async, so after a user edits their profile we read it from the primary for a short window, and we route each user to a consistent replica." Naming read-your-writes and monotonic reads by name shows you've seen the bug before.

06The page in five lines

  1. Async followers lag. Normally by under a second, but "eventually" has no upper bound, and under load it becomes seconds or minutes.
  2. Read-your-writes: users always see their own changes. Read their data from the leader, or wait for a replica that's caught up to their last write.
  3. Monotonic reads: no going back in time. Keep each user on one replica.
  4. Consistent prefix: no effect before its cause. Keep related writes in one partition.
  5. Ask "what if the lag were ten minutes?" If that's not fine, design for it explicitly.
Optional: 30-second recall check 5 questions · click to open · not graded

A user edits their bio and, after a reload, sees the old bio. Which guarantee is missing?

Their own write went to the leader, and the reload hit a lagging follower. Read-your-writes guarantees they see their own updates.

What's the simplest way to give a user monotonic reads?

A single replica only moves forward, so pinning the user (for example by hashing their ID) means they never read an older state.

"Eventually consistent" guarantees that replicas converge within…

"There is no limit to how far a replica can fall behind." Usually it's quick, but nothing promises that.

Readers see a reply before the message it answers. Where is this most likely?

Independent partitions have no global order. Consistent prefix reads need related writes in one partition, or causality tracking.

Why is a log sequence number better than a wall-clock time for "has this replica caught up with my write?"

A position in the leader's log orders writes exactly. Comparing clocks across machines brings back clock-skew problems.
