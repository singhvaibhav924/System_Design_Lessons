Phase 2.3 · Sharding

Sharding: splitting data across machines without creating hot spots

Replication copies everything everywhere. Once the data or the write rate outgrows one machine, you have to split it. This lesson covers how to choose the split, what it does to your indexes and queries, and how to add machines later without moving everything.

Reading time ~25 min Main sources DDIA Ch. 6 "Partitioning" · Alex Xu Ch. 1 "Database scaling" Roadmap topics horizontal & vertical partitioning · shard keys · range vs hash · hot partitions · rebalancing · routing · cross-shard queries
What you'll be able to do Pick a shard key and defend it. Say where hot spots will appear and how you'd relieve them. Explain what sharding costs for secondary indexes, joins and transactions, and why hash(key) % N is the wrong way to assign shards.

01What sharding is, and when to reach for it

DDIA, Ch. 6 introduction and "Partitioning and Replication", Fig. 6-1 — pp. 199–201; Xu, "Database scaling" — pp. 28–30

Partitioning, usually called sharding, breaks a dataset into pieces so that each record belongs to exactly one piece. Each piece is a small database of its own, and different pieces live on different machines. The names vary by product: shard in MongoDB and Elasticsearch, region in HBase, tablet in Bigtable, vnode in Cassandra. The reason is scalability: more disks for the data and more processors for the queries. It's combined with replication (0013), so each partition has a leader and followers, and one machine can be leader for some partitions and follower for others.

Shard last, not first. Xu: scaling up still goes a long way. You can rent a database server with 24 TB of RAM, and in 2013 Stack Overflow served over 10 million monthly visitors from one primary database. Sharding is horizontal partitioning (splitting the rows). Its simpler cousin, vertical partitioning, splits by table or feature instead: users in one database, analytics events in another. Teams usually do that first.

02The shard key: key ranges, hashes, or both

DDIA, "Partitioning of Key-Value Data", Figs. 6-2, 6-3 — pp. 201–205

The goal is an even spread of data and load. If 10 nodes share the load fairly, you get 10× the throughput. If one partition gets most of the load (skew), it becomes a hot spot and the other nine machines sit idle. Placing records randomly would spread them evenly, but then you'd have to ask every node to find anything. Instead the shard key decides where a record lives. Xu: choosing it is "the most important factor".

  • Key range: each partition owns a continuous range, like encyclopedia volumes (A–B, C–D…). Keys stay sorted, so range scans are cheap. Boundaries follow the data, not the alphabet. Used by Bigtable, HBase, and MongoDB before 2.4.
  • Hash of key: each partition owns a range of hash values. Similar keys get scattered, so load spreads well, but range queries must ask every partition. Use a stable hash such as MD5 (Cassandra, MongoDB). Kleppmann warns that Java's hashCode() can differ between processes.
  • Compound key (Cassandra): hash the first part to choose the partition, and sort by the rest inside it. A key of (user_id, timestamp) spreads users across machines, and "this user's posts last week" is still one range scan. That's the equality-then-range rule from lesson 0008, now at the scale of a cluster.
DDIA's sensor example (p. 203): readings keyed by timestamp. Four partitions, 20 active sensors, one minute of writes. Switch the key and compare where writes land with what a "readings for March" query has to touch.

03Hot keys: the celebrity problem

DDIA, "Skewed Workloads and Relieving Hot Spots" — p. 205; Xu, "Celebrity problem" — p. 30

Hashing spreads keys, but not load on a single key. When a celebrity posts, millions of requests hit one user ID, and "the hash of two identical IDs is still the same." Xu's version: if Katy Perry, Justin Bieber and Lady Gaga all hash to one shard, that shard melts. Most databases can't fix this automatically, so it's on the application:

  • Split the hot key. Append a random two-digit number, so post:42 becomes post:42:07. Writes spread over 100 keys and 100 partitions. Reads must now fetch all 100 and combine them, and you must track which keys are split, since doing it for every key would be pure overhead.
  • Give the hottest keys their own shards (Xu), possibly split further.
In your world

A feature store sharded by entity_id works until one entity is a giant: the marketplace's biggest seller, or a bot account sending a million events an hour. Its partition runs hot for both writes and lookups. The fix is the same: split its counters across sub-keys and sum them on read, and cache its features. A "trending items" query that looks at every item is a scatter/gather across all shards; that's the next section.

04Secondary indexes across shards: local or global

DDIA, "Partitioning and Secondary Indexes", Figs. 6-4, 6-5 — pp. 206–209

Sharding by car_id works for "get car 783". But "find red cars" uses a secondary index on colour, and red cars live on every shard. Two designs:

Local index (by document)Global index (by term)
What each shard indexesOnly its own recordsA slice of the terms for all records (e.g. colours a–r on shard 0)
WriteOne shard: simpleMay touch several index shards, so updates are usually asynchronous (DynamoDB: "within a fraction of a second" normally)
Read "red cars"Ask every shard and merge (scatter/gather)Ask one index shard
Used byMongoDB, Cassandra, Elasticsearch, Riak, SolrCloudDynamoDB global secondary indexes, Riak search

Scatter/gather is "prone to tail latency amplification". That's the fan-out maths from lesson 0002: the query is as slow as the slowest of N shards. Vendors therefore advise choosing the shard key so that common queries hit one shard.

05Rebalancing: adding machines without moving everything

DDIA, "Rebalancing Partitions", Fig. 6-6 — pp. 209–214

Data grows, load grows and machines die, so partitions must move. A good scheme shares the load fairly afterwards, stays online during the move, and moves "no more data than necessary". The obvious approach fails the last test:

Kleppmann's example: hash = 123456 lives on node 6 with 10 nodes, node 3 with 11, node 0 with 12. Every resize reshuffles almost everything.
Where the books disagree

Xu's first sharding example assigns users with user_id % 4 (p. 28). It's fine as a picture, but Kleppmann's section heading for it is "How not to do it: hash mod N". Xu agrees later on: "resharding" is listed as a problem, and his fix is consistent hashing (next lesson). In an interview, never leave % N as your final answer.

The approaches that work:

  • Fixed number of partitions, many more than nodes (e.g. 1,000 partitions on 10 nodes). A new node takes whole partitions from the others. The key-to-partition mapping never changes; only partition-to-node does. Riak, Elasticsearch and Couchbase work this way. The catch: the count is fixed at setup and caps your cluster size. Too few partitions and they get huge; too many and the overhead adds up.
  • Dynamic partitioning: split a partition when it grows too big (HBase's default is 10 GB) and merge small ones, like B-tree page splits (0007). It adapts to the data size, but an empty database starts as one partition on one node, so HBase and MongoDB let you pre-split.
  • Fixed partitions per node (Cassandra, 256 per node by default): a new node splits some existing partitions at random points and takes half of each. This is closest to the original consistent hashing 0017.

Automatic or manual? Fully automatic rebalancing is convenient but risky. If an overloaded node is wrongly declared dead, moving its data away adds more load and can cascade (the false-death problem from 0006). Couchbase, Riak and Voldemort propose a new assignment and wait for a human to approve it.

06Request routing: which node has key "foo"?

DDIA, "Request Routing", Figs. 6-7, 6-8 — pp. 214–216

Partitions move, so someone must always know where each one lives. Three placements for that knowledge: (1) any node accepts the request and forwards it; (2) a routing tier forwards requests, acting as a partition-aware load balancer; (3) smart clients connect straight to the right node. Whichever does the routing must learn about changes reliably:

  • A coordination service holds the authoritative partition-to-node map and notifies subscribers. HBase, SolrCloud and Kafka used ZooKeeper; MongoDB has config servers plus mongos routers. Phase 5 · ZooKeeper / etcd
  • Gossip between the nodes themselves (Cassandra, Riak): no external service, and any node can forward. This is the gossip protocol you asked about.

07What sharding costs: joins and transactions

Xu, "Join and de-normalization" — p. 30; DDIA, "Parallel Query Execution" — p. 216

Each partition "operates mostly independently", and that independence is why sharding scales. Anything that crosses shards loses it:

  • Cross-shard joins are hard. Xu's workaround is to denormalize (0011) so each query reads one table on one shard. Analytics warehouses do distribute big joins across nodes (parallel query execution) Phase 12.
  • Cross-shard transactions need coordination between shards, typically two-phase commit, which is slow and fragile Phase 5. Recall VoltDB in lesson 0010: single-partition transactions scale with cores, while cross-partition ones were stuck around 1,000 per second.
  • Global secondary indexes are asynchronous, so a just-written record may not be findable yet (section 04).
The shard-key rule of thumb

Choose the key that your most frequent queries and transactions already filter on (user, tenant, entity), so they stay on one shard. Check it for hot keys and time-ordered writes. Accept scatter/gather only for rare queries.

08The page in five lines

  1. Shard only when one well-replicated node can't hold the data or the writes. Vertical partitioning (by table or feature) usually comes first.
  2. Key range: cheap range scans, but time-ordered keys create hot spots. Hash: even load, no range scans. Compound: hash the first part, sort the rest.
  3. Hot keys survive hashing. Split them with random suffixes (and read all the pieces), or give them their own shards.
  4. Secondary indexes: local means one-shard writes and scatter/gather reads (tail latency). Global means one-shard reads and slower, async writes.
  5. Never hash % N. Use fixed partitions, dynamic splits or partitions per node, plus routing via a coordination service or gossip. Cross-shard joins and transactions are the price.
Optional: 30-second recall check 5 questions · click to open · not graded

Sensor readings are key-range partitioned by timestamp. What goes wrong?

New readings all have "now" timestamps, so one partition takes every write. Prefix the key with the sensor ID to spread them.

You grow from 4 to 5 nodes using hash(key) % N. Roughly how much data moves?

About N/(N+1) of keys change node with mod N. Fixed partitions would move only about 1/(N+1), around 20%.

One celebrity's post gets millions of writes. Why doesn't hash partitioning help?

Hashing spreads different keys. One very hot key still maps to one partition. Split it with random suffixes.

A query filters on a field with a local (document-partitioned) secondary index. What does the database do?

Each shard only indexes its own records, so the query is scattered to all shards and gathered, which amplifies tail latency.

What's the best shard key for a multi-tenant SaaS app whose queries are almost all within one tenant?

Most queries and transactions then stay on one shard. Watch for giant tenants, which are this app's hot keys.
