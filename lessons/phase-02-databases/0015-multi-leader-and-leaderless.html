Phase 2.3 · Replication (part 3)

Many writers: multi-leader and leaderless replication, quorums, and conflicts

Letting more than one node accept writes removes the single leader as a bottleneck and point of failure. In exchange, two writes can conflict and nobody decides the order. This lesson covers how Cassandra-style databases cope, and where it breaks.

Reading time ~25 min Main sources DDIA Ch. 5 "Multi-Leader Replication" and "Leaderless Replication" · Alex Xu Ch. 6 "Design a key-value store" Roadmap topics multi-leader · conflicts · leaderless · quorums (n, w, r) · sloppy quorum · hinted handoff · version vectors
What you'll be able to do Explain when several leaders make sense, the ways write conflicts get resolved and what each one loses, how w + r > n quorums work, why they are not a strong-consistency guarantee, and how version vectors tell "came after" apart from "happened at the same time".

01Several leaders: when it's worth the trouble

DDIA, "Multi-Leader Replication", Fig. 5-6 — pp. 168–171

With one leader, if you can't reach it you can't write. Multi-leader (also called master–master or active/active) lets several nodes accept writes, and each one also follows the others. Within one datacenter "the benefits rarely outweigh the added complexity". The cases where it pays off:

  • Several datacenters, one leader in each. Writes are handled locally and copied to the others asynchronously. That means lower latency, each datacenter keeps going if another fails, and a shaky link between datacenters doesn't block writes.
  • Clients that work offline, like the calendar on your phone and laptop. Each device is a "leader" and syncs later; the lag can be days. CouchDB is built for this.
  • Collaborative editing (Google Docs): every keystroke is applied locally and copied to everyone else.

The price: the same data can be changed in two places at once. Multi-leader support is also often bolted on, with pitfalls around auto-increment keys, triggers and constraints. Kleppmann calls it "dangerous territory that should be avoided if possible."

02Write conflicts, and the ways to resolve them

DDIA, "Handling Write Conflicts", Fig. 5-7 — pp. 171–175

User 1 changes a wiki page title from A to B on leader 1. User 2 changes it from A to C on leader 2. Both succeed locally, and the conflict only shows up later, when it's too late to ask either user. If each leader applied the writes in the order it received them, one would end with B and the other with C, forever. Every scheme must converge: all replicas end up with the same value. The options:

ApproachHowCost
Avoid conflictsSend all writes for a record to the same "home" leader, for example each user's nearest datacenterBreaks down when the home changes (datacenter failure, user moves). "Frequently recommended"
Last write wins (LWW)Highest timestamp or ID wins; the other writes are discarded"Dangerously prone to data loss", with clock problems on top (0006)
MergeCombine the values (e.g. title "B/C"), or use data types built to merge (CRDTs; Google Docs uses operational transformation)Only works where a sensible merge exists
Keep both, resolve laterStore every conflicting version and let application code or the user pick, on write (background handler) or on read (CouchDB)Your code must handle multiple versions

Custom merge logic is easy to get subtly wrong. Amazon's shopping cart kept items added on either side but not items removed, so "customers would sometimes see items reappearing in their carts." Conflicts aren't always the same field changed twice, either. Two bookings of the same room made on different leaders conflict too (write skew, now across datacenters).

With three or more leaders, the topology matters. Ring and star topologies stall if one node fails. All-to-all is sturdier, but writes can overtake each other: an update can arrive before the insert it modifies. That's the causality problem from lesson 0014 again, and timestamps can't fix it.

03Leaderless: write to many, read from many

DDIA, "Leaderless Replication", Fig. 5-10 — pp. 177–179; Xu, Ch. 6 — pp. 94–96

Amazon's in-house Dynamo made a different design popular: no leader at all. Its open-source descendants, "Dynamo-style" databases, include Cassandra, Riak and Voldemort. (Despite the name, AWS's DynamoDB used a different, leader-based design when DDIA was written.) The client, or a coordinator node acting for it, sends each write to all the replicas of that key in parallel and counts it as successful once enough of them confirm. There is no failover: a down replica simply misses some writes.

Reads also go to several replicas, and version numbers show which answer is newest. Missed writes are repaired in two ways:

  • Read repair: when a read finds a stale replica, the client writes the newer value back to it. Good for keys that are read often.
  • Anti-entropy: a background process compares replicas and copies what's missing, in no particular order. Xu adds the usual trick: compare Merkle trees so only the ranges that differ are transferred. Without anti-entropy, rarely read values can stay stale indefinitely.

04Quorums: w + r > n

DDIA, "Quorums for reading and writing", Fig. 5-11 — pp. 179–181

Each key lives on n replicas. A write counts once w of them confirm. A read waits for r replies and keeps the newest version. If w + r > n, the replicas you read from must overlap the replicas that took the write, so at least one of them has the latest value. A common setup is odd n (3 or 5) with w = r = majority: n = 3, w = r = 2 tolerates one node down; n = 5, w = r = 3 tolerates two. Requests always go to all n; w and r only decide how many replies you wait for.

The simulator freezes the moment just after a write: only w replicas have v2 so far (the rest will get it later via replication, read repair or anti-entropy). A read asks r random replicas. "Chance a read is stale" is exact for that moment. Try n = 3, w = 1, r = 1 (fast, often stale), n = 3, w = r = 2, and n = 5, w = 5, r = 1 (fast reads, but one dead node blocks all writes).

Xu's tuning shortcuts: w = n and r = 1 for fast reads; w = 1 and r = n for fast writes; w + r ≤ n for speed and availability at the cost of stale reads. Under the hood, Cassandra's "consistency levels" (ONE, QUORUM, ALL) are this same choice made per request.

Where the books disagree, and DDIA is right

Xu writes that "if W + R > N, strong consistency is guaranteed" (p. 95). Kleppmann lists the edge cases where stale values still come back: sloppy quorums (below); concurrent writes resolved by LWW (one is silently lost); a write concurrent with a read; a write that reached fewer than w replicas, is reported as failed, but is not rolled back on the replicas it reached; and a replica restored from a stale copy. His conclusion: w and r "adjust the probability of stale values being read, but it's wise to not take them as absolute guarantees." You also don't get read-your-writes or monotonic reads. In an interview, say "quorums make reads usually fresh", not "strongly consistent".

Sloppy quorums and hinted handoff

DDIA, "Sloppy Quorums and Hinted Handoff" — pp. 183–184; Xu, "Handling temporary failures" — p. 101

If a network problem cuts a client off from a key's home replicas, should writes fail? A sloppy quorum accepts them on other reachable nodes instead, like sleeping on a neighbour's couch when you're locked out. Once the network heals, those nodes pass the writes back to the home replicas: hinted handoff. This improves write availability, but it "isn't a quorum at all in the traditional sense", because a read of r home replicas may not see the write yet. In DDIA's time, Riak enabled it by default, while Cassandra and Voldemort didn't.

05Concurrent writes: "after" or "at the same time"?

DDIA, "Detecting Concurrent Writes", Figs. 5-12 to 5-14 — pp. 184–191

Leaderless systems get conflicts even with strict quorums: two clients write the same key, and different replicas receive the writes in different orders. The two fixes:

Last write wins keeps the highest timestamp and drops the rest. It was "the only supported conflict resolution method in Cassandra". It converges, but concurrent writes that were all reported as successful are "silently discarded". Kleppmann's safe pattern: make keys write-once (e.g. a UUID key per event), so updates never compete.

Track causality. Operation A happens before B if B knew about A or built on it. Two operations are concurrent if neither knew about the other, whatever the clock said. If one happened before the other, the later one may overwrite; if they're concurrent, both must be kept. In DDIA's shopping-cart example, the server gives each key a version number. A client must send back the version it last read, and the server overwrites only what that client had seen. Concurrent values are kept side by side as siblings, and the client merges them, for example as the union of both carts, with tombstones so removed items don't come back.

With several replicas, one counter isn't enough. Each replica keeps its own counter, and the set of counters is a version vector. Xu's worked example (he calls it a vector clock):

VersionVectorRelation
D2[Sx:2]Written twice via server Sx
D3[Sx:2, Sy:1]Built on D2, written via Sy
D4[Sx:2, Sz:1]Also built on D2, via Sz. Concurrent with D3: each is ahead in one counter
D5[Sx:3, Sy:1, Sz:1]A client merged D3 + D4. ≥ both in every counter, so it supersedes both

The rule: X came before Y if every counter in Y is ≥ the matching counter in X. If each is bigger somewhere, they're concurrent siblings. No clocks are involved. (Xu, pp. 97–99.)

In your world

An online feature store on Cassandra where one pipeline overwrites "latest features for user X" is a fine fit for LWW: there's one writer per key, and losing a superseded value is harmless. A per-user counter updated by several services at once is not: concurrent increments get dropped. Use the database's counter type, a mergeable data type, or route each key to one writer. And remember that a quorum read right after a write isn't a promise you'll see that write.

07The page in five lines

  1. Multi-leader suits multiple datacenters, offline clients and collaborative editing. The price is write conflicts. Avoid it when you can.
  2. Conflict fixes: route each record to one home leader; LWW (loses data); merge (CRDTs, operational transformation); keep siblings for the app to resolve.
  3. Leaderless: write to all n, wait for w; read r, take the newest; read repair and anti-entropy (Merkle trees) fill gaps. No failover.
  4. w + r > n means read and write sets overlap, so reads are usually fresh, but edge cases (sloppy quorums, LWW, partial writes) mean it's not a guarantee.
  5. Concurrent = neither knew of the other. Version vectors detect it without clocks; LWW just drops one. Write-once keys make LWW safe.
Optional: 30-second recall check 5 questions · click to open · not graded

With n = 5, which w and r give overlapping read and write sets?

Overlap needs w + r > n. Only 3 + 3 = 6 is greater than 5.

Two clients write the same key at the same moment, and the store uses last write wins. What happens?

LWW converges by throwing away every write except the one with the highest timestamp, even though all were acknowledged.

Version vectors [A:2, B:1] and [A:1, B:2]. How are they related?

Neither is ≥ the other in every counter, so neither knew about the other. Keep both as siblings.

What does a sloppy quorum trade away?

Writes land on stand-in nodes outside the key's home replicas, so reading r home replicas may miss them until hinted handoff completes.

When does multi-leader replication make the most sense?

Local writes per datacenter (and offline devices) are the main win. Within one datacenter the conflicts aren't worth it.
