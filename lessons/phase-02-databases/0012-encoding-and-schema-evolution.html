Phase 2 · Encoding & evolution

Encoding and schema evolution: changing a data format without breaking anyone

During a deploy, old and new code run side by side, and old data stays around for years. This lesson covers the rules that let JSON, Protobuf and Avro data survive those changes, and the bugs you get when they're broken.

Reading time ~18 min Main sources DDIA Ch. 4 "Encoding and Evolution" · Chip Huyen, DMLS Ch. 3 "Data Formats" Roadmap topics serialization · backward / forward compatibility · Protobuf · Avro · schema registry
What you'll be able to do Say whether a schema change is safe (adding, removing or renaming a field, or changing its type) in both directions: new code reading old data and old code reading new data. Explain why Protobuf uses field numbers, how Avro avoids them, and why a pickle file from outside is a security risk.

01Old and new code run at the same time

DDIA, Ch. 4 introduction — pp. 111–112

You can't upgrade every machine at once. A rolling upgrade replaces servers a few at a time, and mobile users update whenever they like. So "old and new versions of the code, and old and new data formats, may potentially all coexist in the system at the same time." Two kinds of compatibility keep that working:

Who readsWhose dataDifficulty
Backward compatibilityNew codeWritten by old codeUsually easy: you know the old format and can handle it
Forward compatibilityOld codeWritten by new codeTrickier: old code must ignore things it has never heard of

Encoding (also called serialization or marshalling) turns in-memory objects into bytes for a file or the network; decoding turns them back. Kleppmann avoids the word "serialization" here because it means something unrelated in transactions (lesson 0010).

02Language-specific formats: pickle and friends

DDIA, "Language-Specific Formats" — pp. 113–114

Python's pickle, Java's Serializable and Ruby's Marshal are convenient, but Kleppmann lists "deep problems". They tie you to one language. Versioning and efficiency are afterthoughts. And decoding can create arbitrary objects, so "if an attacker can get your application to decode an arbitrary byte sequence", they can often run code on your machine. His verdict: "generally a bad idea… for anything other than very transient purposes."

In your world

Huyen's format table lists pickle for "Python, PyTorch serialization" (DMLS p. 53). Model checkpoints are often pickles, which is why loading a model file from an untrusted source is a real code-execution risk. It's also why weight-only formats such as safetensors exist. Treat a downloaded .pkl or .pt like a downloaded executable.

03JSON and CSV: universal, slightly broken

DDIA, "JSON, XML, and Binary Variants" — pp. 114–116; DMLS, "Text Versus Binary Format" — p. 57

Text formats are readable and supported everywhere, and they have subtle problems:

  • Numbers are vague. JSON doesn't distinguish integers from floats. Integers above 253 lose precision in JavaScript, which is why Twitter's API sends each 64-bit tweet ID twice, once as a number and once as a string. CSV can round floats too: Huyen's example is 0.12345678901232323 becoming 0.12345678901.
  • No raw bytes. Binary data must be Base64-encoded, which is "hacky" and 33% bigger.
  • Schemas are optional and often skipped, so every reader hard-codes its own interpretation. CSV is "quite vague": what if a value contains a comma?

Still, for exchanging data between organizations, "the difficulty of getting different organizations to agree on anything outweighs most other concerns", so JSON wins there. Inside your own systems, at terabyte scale, a binary format is worth it.

04Protobuf and Thrift: field numbers instead of names

DDIA, "Thrift and Protocol Buffers", Figs. 4-1 to 4-4 — pp. 116–121

Protocol Buffers (from Google) and Thrift (from Facebook) require a schema, and code is generated from it:

message Person {
    required string user_name       = 1;
    optional int64  favorite_number = 2;
    repeated string interests       = 3;
}

The encoded bytes contain no field names, only the field tag (1, 2, 3), a type, and the value. Integers use a variable number of bytes, so 1337 takes 2 bytes instead of 8. Kleppmann encodes the same record in every format:

field names in every recordschema-based, no field names
JSON (no whitespace)81 bytes
MessagePack (binary JSON)66 bytes
Thrift BinaryProtocol59 bytes
Thrift CompactProtocol34 bytes
Protocol Buffers33 bytes
Avro32 bytes
The record {"userName": "Martin", "favoriteNumber": 1337, "interests": ["daydreaming", "hacking"]}, sizes from DDIA pp. 116–122. "Binary JSON" saves little because it still spells out every field name; leaving the names out roughly halves the size.

The evolution rules follow from the field tags

DDIA, "Field tags and schema evolution" and "Datatypes and schema evolution" — pp. 120–121

The tag is the field's identity in the data, so:

ChangeNew code reads old data
(backward)		Old code reads new data
(forward)		Why
Add a field with a new tag, optional or with a default✓✓Missing field → default. Unknown tag → old code skips it (the type says how many bytes to skip)
Add a required field✗✓Old data doesn't have it, so the required check fails
Rename a field (same tag)✓✓Names never appear in the encoded data
Remove an optional field✓✓But never reuse its tag; old data with that tag still exists
Remove a required field✓✗Old code still demands it
Change a tag, or reuse an old one✗✗All existing data now means something else
int32 → int64✓riskyOld code holds the value in 32 bits, so large values get truncated
optional → repeated (Protobuf)✓✓New code sees a 0- or 1-item list; old code sees the last item

Because "required" fields make evolution so fragile, newer Protobuf (proto3) dropped the required keyword entirely, so every field is optional with a default.

05Avro: no tags, two schemas

DDIA, "Avro", Figs. 4-5, 4-6 — pp. 122–127

Avro (from the Hadoop world) goes further. The bytes are just values one after another, with no tags and no types, which makes it the smallest at 32 bytes. You can only decode them if you know the schema they were written with. The trick is that the writer's schema and the reader's schema "don't have to be the same, they only need to be compatible". At read time the Avro library puts the two side by side and matches fields by name. Fields only the writer has are ignored. Fields only the reader has get the reader's default.

  • Rule: "you may only add or remove a field that has a default value." Null is allowed only if you say so explicitly (union { null, long }).
  • Renames use aliases in the reader's schema: backward compatible, not forward.
  • Where does the reader find the writer's schema? In a big file, it's written once in the header. For individually stored records, each record carries a schema version number that is looked up in a store of schemas. Over a connection, the two sides agree on it at the start. A store of schema versions also lets you check compatibility before deploying. Phase 4 · Kafka's schema registry
  • Why no tags? Schemas can be generated automatically, for example one per database table for a nightly export. Nobody has to assign tag numbers by hand when a column is added.

06Data outlives code

DDIA, "Dataflow Through Databases", Fig. 4-7 — pp. 129–131

Storing data is "sending a message to your future self". A database can hold values written five milliseconds ago next to values written five years ago, still in their original encoding. A deploy replaces code in minutes, but "data outlives code". So databases need both directions: backward (new code reads old rows) and, during a rolling upgrade, forward (not-yet-upgraded code reads rows that new code just wrote).

The quiet data-loss bug

New code adds a field and writes it. Old code, still running, reads that record into its own model object, which has no slot for the new field, changes something, and writes the object back. The new field is gone. The encoding formats can keep unknown fields, but your application's decode-into-object-and-re-encode step may drop them (DDIA Fig. 4-7). Kleppmann: "not a hard problem; you just need to be aware of it."

For archives and analytics, re-encode the whole dump in the latest schema, and consider a column-oriented format such as Parquet. Huyen: row formats (CSV) suit writing and reading whole examples; column formats suit reading a few features out of thousands. Her 14 MB CSV became a 6 MB Parquet file (DMLS pp. 54–57). Phase 12 · column storage

In your world

A model-serving API with a request schema is exactly this problem. During a canary or rolling deploy, v1 and v2 servers run together, and clients update on their own schedule. Adding an optional feature field with a sensible default is safe. Making a new feature required, or reusing a dropped field's number for a different feature, breaks either old clients or old servers, often silently, with a default value sliding into the model. The same rules apply to a feature-pipeline table read by both last month's training job and today's.

07The page in five lines

  1. Backward = new code reads old data. Forward = old code reads new data. Rolling deploys and stored data need both.
  2. Avoid language-specific formats (pickle) for anything durable or untrusted: they lock you into one language, version poorly, and can execute code.
  3. JSON/CSV: universal but vague (big integers, float precision, no bytes). Fine between organizations; costly at scale.
  4. Protobuf/Thrift: field tags are the identity. Add with a new tag and a default; never reuse or change a tag; never add a required field.
  5. Avro: writer's schema vs reader's schema, resolved by name; add or remove only fields with defaults; keep schema versions in a registry. Old code must not drop unknown fields.
Optional: 30-second recall check 5 questions · click to open · not graded

During a rolling deploy, a v1 server reads a record just written by a v2 server. Which property is needed?

Old code reading data written by newer code is forward compatibility. It works only if old code ignores what it doesn't recognize.

In Protobuf, why can you rename a field but never change its number?

The tag is the field's identity in the bytes. The name only lives in the schema and generated code.

You drop field 7 from a Protobuf schema. What must you never do afterwards?

Old records with tag 7 still exist. A new field with tag 7 would misread them as the new meaning.

How does an Avro reader decode bytes that carry no field tags or types?

The writer's schema (from the file header, a version number lookup, or the connection) is matched by name against the reader's schema.

Why is loading an untrusted pickle file dangerous?

Language-native decoders can instantiate arbitrary classes, which "often allows them to do terrible things such as remotely executing arbitrary code".
