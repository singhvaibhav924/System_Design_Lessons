Phase 2.3 · Sharding (part 2)

Consistent hashing: the ring, virtual nodes, and why only 1/N of keys move

The roadmap says this "deserves serious attention", and interviewers agree. It's the standard answer to "how do you add a cache or database server without reshuffling everything?" Here it is step by step, including the parts the usual explanation leaves out.

Reading time ~18 min Main sources Alex Xu Ch. 5 "Design Consistent Hashing" · DDIA Ch. 6 (consistent hashing side note, rebalancing) Roadmap topics consistent hashing · hash ring · virtual nodes · rebalancing · hot keys
What you'll be able to do Draw the hash ring from memory. Explain which keys move when a server joins or leaves, and why only about 1/N do. Say what virtual nodes fix and what they cost, place replicas on the ring, and state honestly what consistent hashing does not solve.

01The problem: hash % N reshuffles everything

Xu, "The rehashing problem", Figs. 5-1, 5-2 — pp. 72–74

Xu starts with cache servers: serverIndex = hash(key) % N. It's even and simple, until N changes. If server 1 of 4 dies, every key is recomputed with % 3, and "most keys are redistributed, not just the ones originally stored in the offline server." For a cache that means "a storm of cache misses": almost every lookup goes to a server that doesn't have the data, and the database behind the cache takes the full load at once. Lesson 0016's widget measured it: about N/(N+1) of keys move. We want only the keys that have to move to move.

02The ring

Xu, "Hash space and hash ring" to "Remove a server", Figs. 5-3 to 5-9 — pp. 75–78
  1. Bend the hash space into a circle. A hash function outputs numbers from 0 to a maximum (SHA-1: 0 to 2160 − 1). Join the two ends.
  2. Put servers on the ring by hashing their name or IP. There's no % N anywhere.
  3. Put keys on the ring with the same hash. A key belongs to the first server clockwise from it.

Now see what a change costs. Adding server s4 takes over only the arc between it and the server just before it (anticlockwise); every other key keeps its server. Removing s1 hands only s1's keys to the next server clockwise. On average about k/n keys move (k keys, n servers), which is the minimum possible. To find exactly which keys are affected, walk anticlockwise from the changed server to the previous server; that arc is the one that changes hands.

03Two flaws of the basic ring, and virtual nodes

Xu, "Two issues in the basic approach" and "Virtual nodes", Figs. 5-10 to 5-13 — pp. 79–82

With one point per server, positions are random, so:

  • Arcs are uneven. One server may own a tiny slice and another a huge one. Xu's Fig. 5-11 shows most keys on server 2 while servers 1 and 3 hold nothing.
  • Removal dumps everything on one neighbour. When s1 leaves, its whole arc goes to s2, which can suddenly have twice its fair share.

The fix is virtual nodes: each physical server gets many points on the ring (s0_0, s0_1, s0_2…) and owns many small arcs scattered around it. Averages smooth out the randomness. The experiment Xu cites found the spread of load (standard deviation) was about 10% of the mean with 100 virtual nodes and 5% with 200. When a server leaves, its many small arcs are taken over by many different servers. A bonus: give a bigger machine more virtual nodes and it takes proportionally more load (Xu calls this heterogeneity). The cost is more metadata to store and keep in sync.

3,000 keys (140 drawn). Ticks are server points, dots are keys. Try it with 1 virtual node: note the uneven shares, then remove s1 and watch one neighbour take everything. Then switch to 200 virtual nodes and repeat. "Keys moved" stays near 1/N either way; what changes is how evenly load is shared.

04Replicas on the ring

Xu, Ch. 6, "Data partition" and "Data replication", Figs. 6-4, 6-5 — pp. 93–94

The ring also decides where copies go, which is how Dynamo-style stores (0015) choose a key's n replicas. From the key's position, walk clockwise and take the first n distinct physical servers. You skip extra virtual nodes of a server already chosen, otherwise two "replicas" could be the same machine. For safety, Xu also places replicas in different datacenters, because machines in one datacenter often fail together.

05What the usual explanation leaves out

DDIA, "Consistent Hashing" box and "Partitioning proportionally to nodes" — pp. 204, 212–213; DDIA, "Skewed Workloads" — p. 205
It doesn't fix a hot key

Xu lists "mitigate hotspot key problem" as a benefit (p. 85). That's true only for several hot keys that would otherwise land together; the ring spreads different keys. A single celebrity key still hashes to one point and therefore one server. As Kleppmann puts it, "the hash of two identical IDs is still the same." You still need the fixes from 0016: split the key, give it a dedicated server, or cache it.

The name is used loosely. Kleppmann notes that consistent hashing was defined (Karger et al.) for spreading load across internet-wide caches such as CDNs, and that "consistent" here has nothing to do with replica or ACID consistency. For databases he says the literal algorithm "doesn't work very well", that documentation using the term "is often inaccurate", and that it's clearer to say hash partitioning. What databases actually run is closest to his third rebalancing scheme: Cassandra gives each node 256 random points (tokens) by default, so a new node takes slices from many existing nodes. That's virtual nodes under another name.

Where it's used, per Xu: Amazon Dynamo's partitioning, Cassandra, Discord, Akamai's CDN, and Google's Maglev load balancer. DDIA adds Ketama, a widely used library for distributing cache keys. The common thread is many independent clients agreeing on which server owns a key, without a central lookup table, while servers come and go.

In your world

Any time you spread a cache across replicas (an embedding cache, a feature cache, a cache of model outputs), consistent hashing on the cache key means scaling from 8 to 9 pods invalidates about 1/9 of the cache instead of almost all of it. That avoids a burst of misses hitting your feature store or GPU fleet right when you added capacity because load was high. The same idea, "send requests with the same key to the same replica so its cache is warm", shows up in LLM serving when requests that share a prompt prefix are routed together Phase 13.

The 60-second interview version

"Modulo hashing remaps almost every key when the server count changes. Instead, hash servers and keys onto a ring; a key belongs to the next server clockwise. Adding or removing a server moves only the neighbouring arc, about 1/N of the keys. Random positions give uneven arcs, so each server gets ~100–200 virtual nodes, which evens out the load, spreads a dead server's keys across all survivors, and lets bigger machines take more. Replicas are the next N distinct servers clockwise, in different zones. It doesn't fix a single hot key; that needs splitting or caching."

06The page in five lines

  1. hash % N moves about N/(N+1) of keys on any resize, which means a cache-miss storm. Consistent hashing moves about 1/N.
  2. Ring: hash servers and keys into one circular space; a key goes to the first server clockwise. A change only affects the arc back to the previous server.
  3. Basic ring: uneven arcs, and a dead server dumps everything on one neighbour. Virtual nodes (100–200 per server): even load, spread-out failover, weighting by capacity.
  4. Replicas: the next n distinct physical servers clockwise, ideally in different zones.
  5. It does not fix a single hot key. In databases it's really "hash partitioning with many random tokens per node" (Cassandra: 256).
Optional: 30-second recall check 5 questions · click to open · not graded

On a hash ring, which server stores a key?

Walk clockwise from the key's position; the first server point you meet owns it.

A new server joins the ring. Which keys move to it?

Only the arc from the previous server up to the new one changes owner, about 1/N of keys.

Why add virtual nodes when keys already move minimally?

Many small arcs per server average out random placement; a removed server's arcs go to many different successors.

With virtual nodes, how do you pick three replicas for a key?

Skip extra virtual nodes of an already chosen server, otherwise two replicas could be the same machine.

A single viral post's key gets millions of reads. Does consistent hashing fix this?

Identical keys have identical hashes. Hot single keys need splitting, dedicated servers, or caching.
