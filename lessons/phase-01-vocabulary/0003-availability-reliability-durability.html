Phase 1.3 · Availability

Availability, reliability, durability, and what the "nines" really cost

Three promises that sound alike and aren't, and how teams turn them into numbers they can manage.

Reading time ~18 min Main sources DDIA Ch. 1 "Reliability" · Google SRE book (SLOs, Embracing Risk) · Xu Ch. 2 Roadmap topics availability, reliability, durability, SLA/SLO/SLI, error budgets, nines, downtime, graceful degradation, failover
What you'll be able to do Tell availability, reliability and durability apart. Turn "four nines" into real minutes. Work out the availability of a chain of services (and see why it's lower than you'd expect). Explain SLIs, SLOs, SLAs and error budgets the way an SRE would.

01Three different promises

The roadmap's warning: 99.9% availability ≠ 99.9% reliability ≠ 99.9% durability. Each word answers a different question.

The question it answersMeasured as
AvailabilityCan I use it right now?Fraction of time it's up, or fraction of requests that succeed
ReliabilityDoes it keep working correctly, even when things go wrong?Correct results, at the needed speed, despite faults
DurabilityOnce I've stored data, will it still be there later?Probability of not losing data over a period (usually a year)
DDIA, Ch. 1, "Reliability" — p. 6

Reliability is the broadest. Kleppmann defines it as, roughly, "continuing to work correctly, even when things go wrong." "Correctly" includes doing the right thing, at good-enough performance, and without letting attackers in. So reliability covers more than being up: a system that answers instantly with wrong data is available but not reliable.

AWS, S3 data durability

The cleanest real example of availability and durability being different is Amazon S3. AWS says S3 Standard is "designed to provide 99.999999999% durability and 99.99% availability of objects over a given year." That's 11 nines of durability and only 4 nines of availability. S3 may be unreachable for close to an hour a year, but data you've stored there is almost never lost. It becomes reachable again later; it doesn't disappear. A cache is the opposite: it can be highly available with zero durability, because losing its contents is allowed by design.

In your world

Chip Huyen points out that "ML systems often fail silently." A model server can return HTTP 200 with fast, confident, wrong predictions (for example, after the input data changed). Every uptime dashboard says 100% available. The system is still not reliable. For ML, availability is the easy part. Correctness needs its own monitoring. (DMLS Ch. 8, p. 227)

02Faults vs failures

DDIA — pp. 7–10

Kleppmann makes one distinction that the rest of system design builds on:

  • A fault is one component misbehaving: a disk dies, a process crashes, one request times out.
  • A failure is the whole system no longer giving users the service they need.

You can't get faults to zero, so the goal is to stop faults from becoming failures. A system that can do that is called fault-tolerant. It only tolerates certain faults, though. As Kleppmann puts it, surviving Earth being "swallowed by a black hole" would require "web hosting in space — good luck getting that budget item approved."

Three sources of faults, and why the third type is the dangerous one

  1. Hardware faults. Disks have a mean time to failure of about 10–50 years, so "on a storage cluster with 10,000 disks, we should expect on average one disk to die per day." These faults are mostly random and independent, so redundancy handles them well.
  2. Software errors. These are correlated: the same bug runs on every server. A leap second on 30 June 2012 "caused many applications to hang simultaneously" because of a Linux kernel bug. Other examples include a runaway process eating shared resources, a slow dependency, and cascading failures.
  3. Human errors. One study found "configuration errors by operators were the leading cause of outages," while hardware played a role in only 10–25% of them. The fixes are good defaults, sandboxes, testing, quick rollback, gradual rollouts and good monitoring.
The connection to lesson 0001

Redundancy (extra copies) protects against independent faults. It does nothing against correlated ones: a bad deploy or a poison input crashes every copy at once. That's the same lesson as fault domains, applied to software. When someone says "we have 3 replicas, so we're safe", ask: safe from what?

Kleppmann also mentions a counter-intuitive practice: deliberately causing faults, e.g. randomly killing processes, so that the recovery machinery is exercised all the time. Netflix's Chaos Monkey is the best-known example.

03The nines, in real minutes

Xu, Ch. 2, "Availability numbers" — open in your PDF

Availability is written as a percentage, and people talk about the number of nines: 99.9% is "three nines". Xu notes that cloud providers (Amazon, Google, Microsoft) "set their SLAs at 99.9% or above." The percentages all look close together, so it helps to convert them into time:

AvailabilityDown per yearPer monthPer day
99% (two nines)3.65 days7.2 hours14.4 min
99.9% (three)8.76 hours43.2 min1.44 min
99.99% (four)52.6 min4.32 min8.6 s
99.999% (five)5.26 min26 s0.86 s

Each extra nine cuts the allowed downtime by 10×. A useful rule of thumb: at five nines you have about five minutes a year, which is less time than it takes a person to notice an alert, log in and start investigating. So five-nines systems have to recover automatically. A human in the loop alone uses up the budget.

Pick a target or type one. The last line shows the same target counted in failed requests instead of minutes (section 05 explains why that matters).

04Combining parts: chains lose nines, copies add them

A real request passes through many components. Their availabilities combine in two ways:

  • In series (every part must work, e.g. gateway → API → feature store → model): multiply the availabilities. Four services at 99.9% each give 0.9994 ≈ 99.6%, which is about 35 hours of downtime a year instead of 8.8. A chain is always less available than its weakest link.
  • In parallel (any one copy is enough, e.g. two replicas behind a load balancer): the system is down only when all copies are down, so it's 1 − (1 − a)k. Two copies at 99% each give 1 − 0.01² = 99.99%. Copies add nines.
Things to notice: (1) with 1 copy, adding services to the chain steadily removes nines. (2) Going to 2 copies brings it back, even with a long chain. (3) Untick "fail independently": now the copies share the same bug or rack, and the extra copies stop helping.
The fine print

The parallel formula assumes copies fail independently and that switching between them (failover) works instantly and correctly. In practice, failover is itself a component that can fail, and correlated faults (section 02) are common. Treat the math as a best case. It's very useful for spotting the weak link, not for promising customers a number.

Two ways to improve availability

Availability depends on how often things break and how long they stay broken. The standard reliability-engineering formula:

availability  =  MTBF / (MTBF + MTTR)
  MTBF = mean time between failures  (how often it breaks)
  MTTR = mean time to recovery       (how long it stays broken)

A service that fails once a month (720 hours) and takes 1 hour to fix is 99.86% available. Cut the fix to 5 minutes and it's 99.988%, almost another nine, without failing any less often. This is why fast detection, automatic failover, quick rollback and the ability to restart cleanly matter as much as preventing failures.

05SLI, SLO, SLA: how teams put numbers on it

Google SRE book, Ch. 4 "Service Level Objectives". Free online, and the standard reference for this vocabulary.

These three terms show up constantly in interviews and on-call life. The Google SRE book's definitions:

What it isExample
SLI
indicator		"a carefully defined quantitative measure of some aspect of the level of service"Fraction of requests that succeed in under 300 ms
SLO
objective		"a target value or range of values for a service level that is measured by an SLI"That fraction ≥ 99.9% over a rolling 30 days
SLA
agreement		"an explicit or implicit contract with your users that includes consequences"Below 99.5% in a month → customers get a 10% credit

The SRE book's test for SLO vs SLA: ask "what happens if the SLOs aren't met?" If the answer involves money or penalties, it's an SLA. Teams usually set the internal SLO stricter than the external SLA, so they get warned before they owe anyone money.

Measuring availability: by time or by requests

The classic definition is time-based: the share of time the service was up. The SRE book prefers the request-based version for large systems: "the fraction of well-formed requests that succeed, sometimes called yield." The reason is that a big distributed system is rarely completely down. It's usually partly down: one shard, one region, 3% of requests failing. Time-based uptime can't express "3% broken for 2 hours". Request-based availability can.

The SRE book's advice on choosing SLOs: "Don't pick a target based on current performance", "Keep it simple", "Avoid absolutes", and "Have as few SLOs as possible."

06Error budgets: unreliability you're allowed to spend

Google SRE book, Ch. 3 "Embracing Risk"

The SRE book states flatly that "100% is probably never the right reliability target." Two reasons:

  • Users can't tell. "A user on a 99% reliable smartphone cannot tell the difference between 99.99% and 99.999% service reliability!" Their phone, Wi-Fi and mobile network fail far more often than your service does.
  • Each nine costs more and slows you down. More redundancy, more process, fewer and more careful releases.

So the SLO also defines how much failure is acceptable. That gap is the error budget: error budget = 1 − SLO. A 99.9% SLO over 30 days gives a budget of 43 minutes, or, counted by requests, 1 failed request in every 1,000. In the book's words, it's "the 'budget' of how much 'unreliability' is remaining."

The budget turns a recurring argument between product teams ("ship faster!") and operations ("stop breaking things!") into a rule:

  • Budget left → releases go out and risky experiments are fine.
  • Budget used up → "releases are temporarily halted" and the team works on reliability until it's back within the SLO.
A story worth remembering

Google's internal lock service, Chubby, was so reliable that other teams started assuming it could never go down and built in hard dependencies on it, so when it did fail, they failed too. So SRE made sure Chubby "meets, but does not significantly exceed, its service level objective". In a quarter with no real outage, they deliberately took it down to expose those hidden dependencies. Being more available than you promise can be a problem too.

07Graceful degradation: failing partly instead of completely

The last tool from this part of the roadmap. Graceful degradation means that when a part fails, the system keeps working in a reduced form instead of returning errors. A product page with a broken "recommended for you" panel should still let people buy the product. If the personalisation service is down, show the generic bestseller list. If search is slow, return fewer, cached results.

This connects back to faults vs failures: a broken component (fault) only becomes a user-facing failure if the design lets it. Graceful degradation is a deliberate design decision about which features may break without taking the important ones with them.

In your world

Chip Huyen calls the ML version "smooth failing": companies keep "a backup system that is less optimal than the main system but is guaranteed to generate predictions quickly". That could be heuristics, a simple model or "cached precomputed predictions". The rule is then "if the main model takes longer than X milliseconds to generate predictions, use the backup model instead." This is graceful degradation for model serving, and it's a strong thing to mention in ML system design interviews. (DMLS Ch. 11, p. 334)

08The page in five lines

  1. Availability = can I use it now. Reliability = does it work correctly despite faults. Durability = is stored data kept. S3: 11 nines durable, 4 nines available.
  2. A fault is one component breaking. A failure is the whole system letting users down. Redundancy handles independent faults, not correlated ones (bugs, bad configs).
  3. Each nine = 10× less downtime. 99.9% ≈ 8.8 h/year, 99.99% ≈ 53 min, 99.999% ≈ 5 min, which leaves no time for a human to fix things.
  4. Series multiplies (chains lose nines). Parallel adds nines (1 − (1 − a)k) if failures are independent. Availability = MTBF / (MTBF + MTTR), so faster recovery counts as much as fewer failures.
  5. SLI = the measure, SLO = the target, SLA = the contract with penalties. Error budget = 1 − SLO, spent on releases and frozen when used up. Never aim for 100%.
Optional: 30-second recall check 5 questions · click to open · not graded

A model API returns fast HTTP 200 responses, but its predictions became wrong after an upstream data change. It is…

It's up and answering (available), but not working correctly (not reliable). This is the "silent failure" of ML systems.

A request passes through 3 services, each 99.9% available, with no redundancy. The overall availability is about…

In series, multiply: 0.999³ ≈ 0.997. A chain is less available than its weakest link.

You run 3 replicas of a service, all deployed with the same release. A bad release goes out. What protects you?

A bug is a correlated fault: every replica runs the same code and fails the same way. Redundancy doesn't help, but limiting how many users see a release, and undoing it fast, does.

The SRE book's test: "what happens if the SLOs aren't met?" If there are penalties, such as refunds or credits, it's an SLA.
