Phase 1.5 · Distributed-systems fundamentals (part 2)

Clocks lie, processes freeze, and the majority decides

Why no machine can be sure what time it is, whether it's still in charge, or whether another machine is dead, and the two ideas that make systems safe anyway.

Reading time ~20 min Main sources DDIA Ch. 8 "Unreliable Clocks" & "Knowledge, Truth, and Lies" · Alex Xu Ch. 6 Roadmap topics clock problems · heartbeats · failure detection · quorums · leader/lock safety
What you'll be able to do Explain why "use the timestamp to see which write came last" can silently lose data, why a server can't trust its own belief that it's still the leader, and how majority quorums and fencing tokens keep the system correct anyway. These two ideas show up later in replication, Kafka, ZooKeeper and Raft.

Lesson 0005 showed that a timeout tells you only that you stopped waiting. This lesson takes the same uncertainty further. Kleppmann sums up the position of every machine in a distributed system: "A node in the network cannot know anything for sure — it can only make guesses based on the messages it receives (or doesn't receive) via the network."

01Is that node dead? Heartbeats and the false-death problem

DDIA, Ch. 8, "Detecting Faults" and "Timeouts and Unbounded Delays" — pp. 280–281

Many parts of a system need to detect dead machines automatically. A load balancer must stop sending traffic to a dead server. A database must pick a new leader when the old one dies. The usual mechanism is a heartbeat: every node sends a small "I'm alive" message every second or so, and a node that stays silent past a timeout is declared dead.

Sometimes you get a clear signal (a refused connection when the process has crashed), but Kleppmann warns that "you can't count on it." In general a silent timeout is the only signal you get, and it puts you in the same bind as lesson 0005:

  • Timeout too long: users wait or see errors while a truly dead node is still considered alive.
  • Timeout too short: a node that was only slow gets declared dead. If it was in the middle of something, such as sending an email, the replacement may do it again. Worse, its work moves to other nodes, which adds load. If the cluster was already overloaded, this can cascade: "in the extreme case, all nodes declare each other dead, and everything stops working."
Xu, Ch. 6, "Failure detection" — open in your PDF

Xu adds the interview version. "It is insufficient to believe that a server is down because another server says so", so you want at least two independent sources before marking it down. With many nodes, having everyone heartbeat everyone is too expensive, so systems such as Cassandra use a gossip protocol. Each node keeps a list of heartbeat counters, increments its own, and periodically sends the list to a few random nodes, which pass it on. If a node's counter hasn't increased for a while (and others agree), it's marked offline. News spreads through the cluster the way a rumour does, without anyone talking to everyone.

Timing a model's inference with time.time() before and after usually works, until a clock sync lands in the middle and you log a negative or wildly wrong latency. For durations, always use the monotonic clock. Your p99 dashboards from lesson 0002 depend on it.

03Wall clocks are less accurate than they look

DDIA, "Clock Synchronization and Accuracy" — pp. 289–291

Computers keep their wall clock roughly right by regularly syncing with time servers using NTP. Kleppmann's list of what goes wrong:

  • Drift. The quartz crystal runs fast or slow, depending on temperature. Google assumes 200 parts per million. That's 6 ms of error if you resync every 30 seconds, or 17 seconds if you resync once a day.
  • Jumps. A clock that is too far off gets forcibly reset, so programs see time go backwards or leap forward.
  • Sync is only as good as the network. Over the internet, about 35 ms of error is the best achievable, with occasional spikes to around a second. A machine accidentally firewalled off from its time servers can drift unnoticed.
  • Leap seconds make a minute 59 or 61 seconds long, and "have crashed many large systems."
  • Virtual machines get paused for tens of milliseconds while another VM uses the CPU, so from inside, the clock suddenly jumps.
  • User devices can't be trusted at all. People set their phone's clock wrong on purpose, e.g. to cheat in games.

The most dangerous part: a broken clock usually doesn't crash anything. Kleppmann: "most things will seem to work fine", and if software relies on synchronized clocks, "the result is more likely to be silent and subtle data loss than a dramatic crash."

A clock reading is a range, not a point

Your clock may print microseconds, but if it's only accurate to ±100 ms, "the microsecond digits in the timestamp are essentially meaningless." Google's Spanner database is the famous exception that takes this seriously. Its TrueTime API returns [earliest, latest] instead of a single time, and Spanner deliberately waits out that uncertainty (about 7 ms, using GPS receivers and atomic clocks in every data center) before committing, so that the order of transactions is certain. (DDIA pp. 293–295)

04Why "the latest timestamp wins" loses data

DDIA, "Timestamps for ordering events", Fig. 8-3 — pp. 291–293

Suppose two copies of a database receive conflicting writes to the same key. The tempting fix is to tag every write with the wall-clock time and keep the newest one. This is called last write wins (LWW), and Kleppmann notes it is widely used, including in Cassandra and Riak.

His example: client A writes x = 1 on node 1. Shortly afterwards, client B increments it to x = 2 on node 3. Node 3's clock is just 3 ms behind node 1's. That's excellent synchronization, "probably better than you can expect in practice." B's write gets an earlier timestamp than A's, so every replica keeps x = 1 and B's write vanishes.

The defaults recreate DDIA's Figure 8-3 (A = 42.004 s, B = 42.003 s). Data is lost whenever the clock difference is larger than the real gap between the writes. With thousands of writes per second, that gap is often under a millisecond.

Kleppmann lists three problems with LWW: writes "can mysteriously disappear" with no error; it can't tell "B came after A" apart from "A and B happened at the same time without knowing about each other"; and two writes can get identical timestamps. Making clocks more accurate can't fully fix this, because NTP's accuracy is itself limited by network delay. The safer tool for ordering events is a logical clock, which counts events instead of reading the time.

Interview red flag

"We'll resolve conflicts by taking the record with the latest updated_at" sounds reasonable and is often wrong across machines. The strong answer names the risk (clock skew silently drops writes) and either accepts it on purpose (e.g. for a "last seen online" field where losing an update doesn't matter) or uses something safer (a single leader that decides order, version numbers, or conflict-free merging).

05Any process can freeze at any moment

DDIA, "Process Pauses" — pp. 295–299

Clocks aren't the only problem. A program can also stop running for a while without noticing. Kleppmann's example: a leader holds a lease (a lock that expires automatically, say after 30 seconds, unless renewed). Its loop checks "does my lease still have 10 seconds left?" and then processes a request. What if the thread freezes for 15 seconds between the check and the processing? By the time it continues, the lease has expired, another node is now leader, and this node goes ahead anyway.

Is a 15-second freeze realistic? Kleppmann's list of causes:

  • Garbage collection. "Stop-the-world" pauses "have sometimes been known to last for several minutes!"
  • Virtual machines being suspended or live-migrated to another host, for an arbitrary length of time.
  • The CPU being given to other threads or VMs on a heavily loaded machine.
  • Slow disk I/O, including disks that are really network storage (e.g. Amazon EBS).
  • Swapping: memory pressure forces the OS to move memory to disk, and in the worst case the machine spends all its time swapping.
  • A laptop lid closing, or an operator accidentally sending Ctrl-Z (SIGSTOP).

The conclusion: "A node in a distributed system must assume that its execution can be paused for a significant length of time at any point, even in the middle of a function. During the pause, the rest of the world keeps moving and may even declare the paused node dead."

In your world

A Python worker that starts swapping while loading a big dataframe, a training node on a VM that gets live-migrated, a feature-pipeline job stuck on slow network storage: from the outside, each one is a node that "went silent" and may be declared dead, then wakes up and carries on as if nothing happened.

06The truth is defined by the majority

DDIA, "The Truth Is Defined by the Majority" — pp. 300–302

Put sections 01–05 together and you get Kleppmann's gothic scenarios. A node whose outgoing messages are being dropped gets "dragged to the graveyard, kicking and screaming 'I'm not dead!'" A node frozen for a minute by garbage collection is declared dead, then "suddenly raises its head out of the coffin, in full health," unaware that any time passed.

The moral: "a node cannot necessarily trust its own judgment of a situation." So instead of letting any one node decide, distributed systems decide by quorum, a vote among nodes. "If a quorum of nodes declares another node dead, then it must be considered dead, even if that node still very much feels alive." The usual quorum is a majority (more than half), and it has one key property:

"There can only be only one majority in the system — there cannot be two majorities with conflicting decisions at the same time." — DDIA, p. 301

If a network split divides 5 nodes into groups of 3 and 2, only the group of 3 can form a majority and keep making decisions. The group of 2 knows it's in the minority and stops. That's how a system avoids split brain. (This is also the CAP trade-off from lesson 0004 in practice: the minority side gives up availability to keep consistency.)

07The zombie leader, and fencing tokens

DDIA, "The leader and the lock" and "Fencing tokens" — pp. 301–304

Systems often need exactly one of something: one leader per database partition, one holder of a lock, one owner of a username. The quorum can decide who that is, but the old holder may not have heard. After a pause, it can come back still believing it's "the chosen one". Kleppmann notes this exact bug existed in HBase: a paused client with an expired lease woke up and wrote to a file that a new lease holder was also writing to, corrupting it.

The fix is fencing tokens. Every time the lock service grants a lease, it also hands out a number that always increases (33, then 34, …). Every write to the protected resource must include the token, and the resource itself rejects any token older than one it has already seen. Step through it both ways:

The design rule

The check must happen at the resource, not in the client. Kleppmann: "it is not sufficient to rely on clients checking their lock status themselves", because the client checking is exactly the part that can be paused or wrong. This is the general pattern: don't trust a node's belief that it's in charge; make the thing being changed verify it. You'll see it again with ZooKeeper, Kafka and Raft, where the token is called a term or epoch number.

One last boundary, from the same chapter: all of this assumes nodes may be slow, paused or out of date, but honest. A node that deliberately lies (e.g. sends a fake token) is a Byzantine fault. Tolerating those needs much heavier protocols, which are used in places like aircraft systems and blockchains, but rarely inside a company's own data center. (DDIA p. 304)

08The page in five lines

  1. Failure detection = heartbeats + timeouts. Too short declares slow nodes dead (duplicate work, cascades). Too long leaves users waiting. Gossip spreads heartbeats cheaply in big clusters.
  2. Use monotonic clocks for durations and timeouts. Wall clocks drift, jump backwards and disagree between machines, and the errors are usually silent.
  3. Last write wins by wall-clock timestamp silently drops writes when clock skew is larger than the gap between writes. Use a single orderer, versions or logical clocks when it matters.
  4. Any process can freeze (GC, VM migration, swapping, slow disk) and wake up acting on outdated beliefs, such as "I hold the lease".
  5. The majority decides, not any single node (3 nodes survive 1 failure, 5 survive 2). Fencing tokens, checked by the resource, stop a zombie leader from doing damage.
Optional: 30-second recall check 5 questions · click to open · not graded

You want to measure how long a model call took. Which clock should you use?

Durations need a clock that only moves forward. A wall clock can be reset mid-measurement.

Two replicas resolve conflicts with "latest timestamp wins". Node B's clock is 5 ms behind. What can happen?

A write made on B less than 5 ms after a write on A gets an earlier timestamp and is thrown away. No error is reported.

Why do voting clusters like ZooKeeper or etcd usually run 3 or 5 nodes rather than 4?

A majority of 4 is 3, so 4 nodes survive only 1 failure, the same as 3 nodes but with more cost.

A lease holder freezes in a long GC pause, its lease expires and another node takes over. What stops the frozen one from corrupting data when it wakes?

The client's own check is the part that can be stale or paused. The resource must enforce ordering with fencing tokens.

A node is declared dead by a majority but feels perfectly healthy. What should it do?

"The individual node must abide by the quorum decision and step down." A node can't trust its own judgment of the situation.
