Phase 1.1 · Scalability

Scaling up, scaling out, and why state is the real problem

Every "design X for millions of users" answer starts with the ideas on this page.

Reading time ~15 min Main sources Alex Xu Ch. 1 · DDIA Ch. 1 & Part II intro Roadmap topics vertical/horizontal scaling, stateless vs stateful, elasticity, bottlenecks, SPOF, fault domains
What you'll be able to do Look at a system and say what breaks first when traffic grows 10×, and explain why getting the state out of the servers is what makes "just add more servers" work.

01"Scalable" is not a yes-or-no word

DDIA, Ch. 1, "Scalability" — open p. 10 in your PDF

People say "X is scalable" all the time. Kleppmann argues that sentence has no meaning by itself:

It is meaningless to say "X is scalable" or "Y doesn't scale." Rather, discussing scalability means considering questions like "If the system grows in a particular way, what are our options for coping with the growth?" — Martin Kleppmann, Designing Data-Intensive Applications, p. 10–11

The phrase that matters is grows in a particular way. Before you can talk about scaling, you have to say which number is growing. Kleppmann calls these numbers load parameters: requests per second, the ratio of reads to writes, how many users are online at once, the cache hit rate, and so on. Pick the wrong one and your scaling work fixes the wrong thing.

DDIA, Ch. 1, "Approaches for Coping with Load" — p. 18

His example: a system built for 100,000 requests/sec of 1 kB each looks nothing like one built for 3 requests/minute of 2 GB each, even though both move about the same amount of data per second. The first is about handling many small requests at once. The second is about moving big files.

In your world

An embedding API getting 5,000 short texts per second and a nightly batch job scoring 200 GB of rows can both be called "the model service". They need completely different designs. When someone says "make the model service scale", the first question is: scale in what? More requests? Bigger inputs? More models? Faster responses?

02Two ways to get bigger

Alex Xu, Ch. 1, "Vertical scaling vs horizontal scaling" — open in your PDF

When one machine can't keep up, you have two options:

  • Scale up (vertical scaling): swap in a bigger machine with more CPU, RAM, disk or a bigger GPU.
  • Scale out (horizontal scaling): add more machines and split the work between them.
Scale up (vertical)Scale out (horizontal)
What you doBuy a bigger boxAdd more boxes
Code changesUsually noneOften big: the work must be splittable
CeilingHard limit: the biggest machine you can buyMuch higher; keep adding machines
Cost curveGrows faster than size: 2× machine costs well over 2×Roughly linear, using cheap standard machines
If it diesEverything is down. It's a single point of failureThe others keep going (if designed for it)
New problemsFewCoordination, consistency, partial failure, network trouble
DDIA, Part II intro, "Scaling to Higher Load" — p. 146

Two details from the books are worth remembering, because candidates often get them wrong:

1. A bigger machine is not proportionally better. Kleppmann notes that a machine with twice the CPUs, RAM and disk "typically costs significantly more than twice as much", and that because of internal bottlenecks "a machine twice the size cannot necessarily handle twice the load."

2. Scaling out has its own price. Spreading work across machines that don't share memory or disk is called a shared-nothing architecture. Each machine is called a node. It lets you use cheap hardware and survive losing a whole data center. But the nodes can only coordinate over a network, and networks are slow and unreliable. Most of this course (Phases 2–5) exists because of that one fact.

The mature take

Scaling up is not the "junior" answer. Xu points out that Stack Overflow in 2013 served 10M+ monthly visitors with one main database server. Kleppmann notes that the common advice "until recently was to keep your database on a single node (scale up) until scaling cost or high-availability requirements forced you to make it distributed." Real systems mix both. In an interview, the strong move is to say why you're scaling out, not to assume you must.

03Bottlenecks, single points of failure, and fault domains

Before adding anything, ask two questions about the current design.

What is the bottleneck?

A request usually passes through several parts in a row: load balancer → web server → database. The whole path can only go as fast as its slowest part. That part is the bottleneck. If the database is at 100% CPU, doubling your web servers just means twice as many servers waiting on the same database. Scaling anything other than the bottleneck is wasted money.

Common interview trap

Drawing "add more servers behind a load balancer" when the scaling problem is in the database. The web tier is usually the easy part to scale (you'll see why in section 04). The data tier is where the hard problems are.

What is a single point of failure?

Xu quotes the definition in Ch. 1, "Cache" section

Xu uses the standard definition: a single point of failure (SPOF) is "a part of a system that, if it fails, will stop the entire system from working." One web server, one database, one cache box or one load balancer: each is a SPOF if nothing takes over when it dies. The fix is redundancy: two or more copies, plus a way to switch over, called failover. Xu's one-line summary of the chapter: "Build redundancy at every tier."

Do my copies fail together?

This term comes from cloud providers, not the two books. AWS's version: Regions and Availability Zones.

Redundancy only helps if the copies don't all fail for the same reason. A fault domain is a group of things that go down together: the same rack (shared power and network switch), the same building, the same availability zone, the same region. Two database copies on two servers in the same rack still count as one fault domain, so one power failure takes out both. That's why Xu's design eventually spreads across multiple data centers.

04The real problem: where does the state live?

Xu, Ch. 1, "Stateless web tier" — open in your PDF

This is the most important idea on the page. State is any data a server has to remember between one request and the next: who is logged in, what's in someone's cart, a user's chat history.

  • A stateful server keeps that data in its own memory or disk. Asha logged in through Server 1, so only Server 1 knows her.
  • A stateless server keeps nothing between requests. It reads what it needs from a shared store every time.

With stateful servers, every request from Asha has to go back to Server 1. Load balancers can do this with sticky sessions, but Xu notes the cost: "Adding or removing servers is much more difficult with this approach. It is also challenging to handle server failures."

Try it below. Each user is already logged in. Click their names to send requests, crash servers, add servers, and switch between the two designs.

Things to notice: (1) with sessions in server memory and no stickiness, the second click on any user logs them out. (2) Turn on sticky sessions: everything works, until you crash a server and its users lose their sessions. (3) Add a server in memory mode: it knows nobody. (4) Switch to "Shared store" and do all of the above. Nobody gets logged out.

In the stateless design the servers become interchangeable. Any server can handle any request, so you can add servers, remove them or lose them without anyone noticing. This is why Xu's first rule for scaling is "Keep web tier stateless."

The part most people miss

Stateless doesn't mean the state disappeared. It moved into a shared store: a database, or something like Redis. The web tier became easy to scale because all the hard parts went into the data tier. Kleppmann says it directly: spreading stateless services across machines is "fairly straightforward", but taking stateful data systems from one node to many "can introduce a lot of additional complexity." That's why the next several phases of this course (databases, caching, queues, distributed systems) are all about the place the state went.

05Elasticity: scaling by itself

DDIA, Ch. 1 — p. 17

An elastic system adds and removes machines automatically as load changes. Most clouds call this autoscaling. Once the web tier is stateless, autoscaling it is easy, because a new server is useful the moment it starts. With stateful servers, a new server starts empty and helps nobody until users get moved to it.

Kleppmann adds a caveat people forget: elastic systems help when load is unpredictable, but "manually scaled systems are simpler and may have fewer operational surprises." Automatic scaling is a tool with its own failure modes. It isn't always better.

In your world

A model inference server is usually stateless. The model weights are read-only and every replica has the same copy, so serving scales out nicely behind a load balancer. Two ML-specific twists: (1) a new replica may take minutes to download and load the weights onto a GPU. That's a cold start, so autoscaling reacts slowly to sudden spikes. (2) GPUs make scaling up (a bigger GPU) a common first step. Truly stateful parts of ML systems, like per-user conversation history, feature stores and the LLM KV cache, are where ML serving gets hard. The same lesson again.

06The map: how one server becomes millions of users

This is the whole of Xu Ch. 1 in one list — read it from the start. It's the best 30-page overview in your resources folder.

Xu's Chapter 1 walks one system from a single server to millions of users. Here is the whole path, so you can see where today's ideas fit and what's coming later. Steps marked today are covered on this page. Purple badges are later phases. You only need to know that they exist for now.

  1. 1One server does everything today Web app, database and cache on one box. Simple, and a single point of failure.
  2. 2Split the web tier from the data tier today Separate machines, so each can be scaled on its own.
  3. 3Load balancer + several web servers today Scale out the web tier and remove its SPOF. Phase 8 for details
  4. 4Database replication One primary takes writes, copies serve reads, and a copy takes over if the primary dies. Phase 2.3
  5. 5Cache tier Keep hot data in memory so the database does less work. Phase 3
  6. 6CDN for static files Images, JS and CSS served from servers near the user. Phase 8
  7. 7Stateless web tier today Sessions move to a shared store, which makes autoscaling possible.
  8. 8Multiple data centers Route users to the nearest one, and send everyone to a healthy one if a data center fails. Introduces data-sync problems. Phases 2 & 5
  9. 9Message queue Slow work (like photo processing) goes on a queue so producers and workers scale separately. Phase 4
  10. 10Logging, metrics, automation You can't run what you can't see. Phase 9
  11. 11Shard the database Split the data itself across machines, which is scaling out the data tier. Phase 2.3

Notice the shape: steps 1–3 and 7 are about the web tier and are fairly mechanical. Almost everything else is about data. That matches what section 04 predicted.

One roadmap item, capacity planning, is mentioned here and skipped on purpose. It's the arithmetic side of scaling ("how many servers for 23K requests/sec?") and gets its own phase.

07The page in five lines

  1. Scalability is a question, not a label: "if this load parameter grows, what are our options?"
  2. Scale up is simple but hits a ceiling, costs more than linearly, and is a SPOF. Scale out has a much higher ceiling but brings network and coordination problems. Real systems mix both.
  3. Find the bottleneck first. Scaling anything else is wasted.
  4. Redundancy only counts across fault domains. Copies that fail together are really one copy.
  5. Stateless servers are interchangeable, so they scale and autoscale easily. The state moved to the data tier, and that's where the hard problems (and most of this course) are.
Optional: 30-second recall check 5 questions · click to open · not graded, just helps it stick

You have 4 web servers and the database is at 100% CPU. Traffic doubles. Adding 4 more web servers will most likely…

The slowest part limits the whole path. More web servers just means more servers waiting on the same overloaded database.

Why is it hard to autoscale a web tier that keeps login sessions in each server's memory?

A new server starts with empty memory, so any logged-in user sent to it gets logged out. Moving sessions to a shared store fixes this.

According to Kleppmann, which is true about scaling up?

A 2× machine usually costs well over 2×, and because of internal bottlenecks it may not handle 2× the load either.

Your two database copies run on two servers in the same rack, sharing one power supply. What's the problem?

One power failure takes out both. Redundancy only helps if the copies fail independently.

A "stateless web tier" means…

The state still exists. It lives in a shared database or cache instead of inside each web server, so the servers are interchangeable.
