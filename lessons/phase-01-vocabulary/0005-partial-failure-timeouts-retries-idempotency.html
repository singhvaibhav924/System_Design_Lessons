Phase 1.5 · Distributed-systems fundamentals

Partial failure, timeouts, retries, and idempotency

A request can succeed even when its caller sees an error. That one uncertainty shapes how reliable services communicate.

Reading time ~16 min Main sources DDIA Ch. 8, 7, 11, 12 · Alex Xu Ch. 10 Roadmap topics partial failure · unreliable networks · timeouts · retries · idempotency
What you'll be able to do Explain why a timeout does not tell you whether a request ran, choose when a retry is appropriate, and describe how an operation ID can prevent a retried request from applying its effect twice.

01A distributed system can be partly broken

DDIA, Ch. 8, “Faults and Partial Failures” — PDF pp. 296–299

On one computer, a failure is often obvious: the program runs, or the computer crashes. With several computers connected by a network, one part can fail while the rest keeps working. Kleppmann calls this a partial failure.

A model server may be healthy while the feature store is unreachable. One database replica may be slow while another still answers. The hard part is that the caller may not know which part failed—or whether anything failed at all.

Distributed services therefore need to assume that communication can be lost, delayed, or duplicated, and that machines can become slow or unreachable independently. The service must decide what behavior users should see when that happens.

02A timeout says “I stopped waiting,” not “it did nothing”

DDIA, Ch. 8, “Unreliable Networks” and “Timeouts and Unbounded Delays” — PDF pp. 300–306

Suppose a client sends a request to charge a customer and waits for the result. If no response arrives, several different things may have happened:

  • The request never reached the service.
  • The service received it but has not finished yet.
  • The service completed the charge, but its response was lost or delayed.

From the client’s point of view, those cases look the same: no response arrived in time. A timeout limits how long the client waits. It cannot reveal whether the server completed the operation.

client                 service
  | ---- charge -------> |
  |                      | charge succeeds
  | <--- response ---X   | response is lost
  |                      |
  | timeout              | the charge already happened

A timeout describes the caller’s wait. It does not roll back work at the service.

Timeouts are necessary because a caller cannot wait forever. But there is no universally correct timeout value. Set it too long and users wait while an unhealthy dependency holds up work. Set it too short and normal variation in network or server response time causes false alarms and unnecessary retries.

DDIA’s practical advice is to measure response-time variation over time and across machines, then choose a timeout that fits the application’s deadline and tolerance for delay. Treat the timeout as a decision point, not proof that the remote machine is dead.

Connection to lesson 0002

Response times are a distribution. A timeout that sits below the service’s ordinary slow tail will fire during healthy but slow periods. Choose it from measured behavior and the user-facing deadline, then make the timeout behavior safe.

03Retries help with transient faults—and can make overload worse

DDIA, Ch. 7, “Handling Errors and Aborts” — PDF pp. 254–255

If an operation fails because of a temporary network interruption or a database failover, trying again may work. If it failed because the request is invalid, retrying the same request will not fix it. And if the service is overloaded, more attempts can add load exactly when it has the least spare capacity.

For a retryable operation, use a bounded number of attempts with increasing waits between attempts (exponential backoff). Stop when the request’s overall deadline is reached. Retry transient failures; surface permanent failures instead.

A retry can duplicate a successful operation

The request may have succeeded and only its response may have been lost. Retrying a payment, counter increment, email send, or job creation can apply the effect twice unless the operation has a duplicate-suppression mechanism.

Retries can also multiply across service layers. If a client, gateway, and application each retry several times, a single user action can turn into many calls to an already struggling dependency. Agree on which layer owns retries, cap attempts, and pass one overall deadline through the call chain.

04Idempotency makes repeating an operation safe

DDIA, Ch. 11, “Idempotence” — PDF p. 500 · Ch. 12, “The End-to-End Argument” — PDF pp. 539–542

An operation is idempotent when applying it multiple times has the same final effect as applying it once.

OperationIdempotent?Why
Set job status to “complete”Usually yesRepeating the same assignment leaves the same status
Increment a counterNoEach retry adds one again
Charge $11 to an accountNo, by itselfA retry can charge another $11

For an operation that is not naturally idempotent, give the user action a stable operation ID. The client sends the same ID every time it retries that action. The service records the ID alongside the effect, with a uniqueness rule enforced atomically. If that ID arrives again, the service does not repeat the effect; it returns the result associated with the first attempt.

For example, a payment request carries payment-request-7f31. The service records that ID and the charge in one database transaction. If the response is lost and the client retries with the same ID, the uniqueness check finds the earlier request and prevents a second charge. A new intentional payment gets a new ID.

In your world

A model prediction is usually safe to recompute, but creating a training run, writing a feature update, or triggering a paid inference job may have side effects. Give each user-initiated action a stable ID and carry it through the services that record or perform that action. A retry of the same action reuses the ID; a new action gets a new one.

This is an end-to-end concern. TCP can suppress duplicate packets within one connection, and a database transaction can protect its own writes. Neither one knows that a client reconnecting later is retrying the same business action. The operation ID has to travel from the original caller through to the place that applies the effect.

05“Exactly once” means one visible effect within a boundary

Networks cannot promise that a request is delivered exactly once: callers may retry after a response is lost. Systems can combine repeatable attempts with duplicate suppression so the visible effect happens once within a defined boundary. That boundary matters. A database can deduplicate its own write, but an email sent outside that database transaction may still be sent twice.

So when someone says “exactly once,” ask: exactly once at which step, and across which side effects? Often the practical goal is at-least-once attempts plus an idempotent or deduplicated effect, not a magical guarantee from the network.

06A compact way to reason about a remote call

  1. What is the deadline? Set a timeout that fits the user-facing operation and measured response times.
  2. What errors are transient? Retry only those, with bounded attempts and increasing delays.
  3. Can a retry repeat a side effect? Make the operation naturally idempotent or attach a stable operation ID.
  4. Where is the effect recorded? Enforce deduplication atomically at that boundary, and pass the ID all the way there.
  5. What happens after the deadline? Return a clear failure or status; do not imply that a timeout rolled back the work.
Optional: quick recall check 3 questions · click to open · not graded

A payment client times out after sending a charge. What can it conclude?

The request or response may have been lost, or the server may still be working. A timeout only ends the caller’s wait.

How should a service retry a temporary failure?

Bounded retries with increasing waits limit extra load. Permanent errors need correction, not repetition.

A charge request might be retried after a lost response. What prevents a second charge?

The same stable ID lets the service recognize the retry and suppress the duplicate effect.
