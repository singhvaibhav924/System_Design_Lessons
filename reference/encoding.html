Reference · Phase 2 (encoding)

Encoding & schema evolution

The short version of Lesson 0012. Sources: DDIA Ch. 4, DMLS Ch. 3.

Compatibility

Backward: new code reads old data (easy). Forward: old code reads new data (must ignore unknowns). Rolling deploys + stored data need both.

DDIA p. 112

Language formats

pickle, Java Serializable, Marshal: one language, poor versioning, slow, and decoding untrusted bytes can run code. Only for transient use. Untrusted .pkl/.pt = executable.

DDIA pp. 113–114

JSON / CSV pitfalls

No int vs float (IDs > 2⁵³ break in JS), no bytes (Base64 +33%), optional schemas, CSV escaping & float rounding. Fine for cross-org interchange.

DDIA pp. 114–115 · DMLS p. 57

Sizes (same record)

JSON 81 B · MessagePack 66 · Thrift Binary 59 · Thrift Compact 34 · Protobuf 33 · Avro 32. Dropping field names is what saves space.

DDIA pp. 116–122

Protobuf / Thrift rules

Tag = identity. Rename ok. Add only optional/default with a new tag. Remove only optional; never reuse its tag. Never change a tag. int32→int64 truncates in old code. proto3: no required.

DDIA pp. 120–121

Avro

No tags or types in bytes. Writer's vs reader's schema resolved by field name. Add/remove only fields with defaults. Null only via union. Renames via aliases (backward only).

DDIA pp. 122–125

Where's the writer's schema?

File header (object container) · per-record version number + schema store (registry) · negotiated per connection. Registry also checks compatibility before deploy.

DDIA pp. 125–126

Data outlives code

DB holds 5-year-old encodings next to new ones. Old code decoding into objects and re-saving can drop new fields (Fig. 4-7).

DDIA pp. 129–130

Row vs column formats

Row (CSV, Avro): write/read whole records. Column (Parquet): read a few features of many; 14 MB CSV → 6 MB Parquet. pandas is column-major.
