Reference · Phase 2 (replication)

Replication

The short version of Lesson 0013. Lessons 0014–0015 will add replication lag and multi-leader / leaderless replication. Source: DDIA Ch. 5.

Why replicate

Latency (near users) · availability (survive failures) · read throughput. Hard part = changes. Three algorithms: single-leader, multi-leader, leaderless.

DDIA p. 151

Single leader

All writes → leader → ordered replication log → followers apply in order. Reads anywhere. PostgreSQL, MySQL, MongoDB, Kafka. Scales reads, not writes.

DDIA pp. 152–153 · Xu p. 12

Sync / async / semi-sync

Sync: safe copy, but a slow follower blocks writes. Async: never blocks, but acknowledged writes can be lost on failover. Semi-sync: one sync follower → every ack on ≥ 2 nodes.

DDIA pp. 153–155

New follower

Lock-free consistent snapshot + its exact log position (PG LSN, MySQL binlog coordinates) → copy → replay backlog → caught up.

DDIA pp. 155–156

Follower failure

Catch-up recovery: ask the leader for changes since the last applied one.

DDIA p. 156

Failover

Detect (timeout ~30 s) → choose most up-to-date follower (election/controller) → reconfigure clients and the old leader.

DDIA p. 157

Failover pitfalls

Lost async writes discarded · other systems diverge (GitHub reused auto-increment keys → private data leaked via Redis) · split brain (STONITH) · timeout too short/long. Many teams fail over manually.

DDIA pp. 157–158

Replication logs

Statement (NOW()/RAND() break) · WAL shipping (byte-level, version-locked, PG/Oracle) · logical row-based (decoupled, enables CDC, MySQL binlog) · trigger-based (flexible, slow).
