Reference · Phase 2 (replication)

Replication

The short version of Lesson 0013. Replication lag: Lesson 0014. Multi-leader & leaderless: Lesson 0015. Source: DDIA Ch. 5.

Why replicate

Latency (near users) · availability (survive failures) · read throughput. Hard part = changes. Three algorithms: single-leader, multi-leader, leaderless.

DDIA p. 151

Single leader

All writes → leader → ordered replication log → followers apply in order. Reads anywhere. PostgreSQL, MySQL, MongoDB, Kafka. Scales reads, not writes.

DDIA pp. 152–153 · Xu p. 12

Sync / async / semi-sync

Sync: safe copy, but a slow follower blocks writes. Async: never blocks, but acknowledged writes can be lost on failover. Semi-sync: one sync follower → every ack on ≥ 2 nodes.

DDIA pp. 153–155

New follower

Lock-free consistent snapshot + its exact log position (PG LSN, MySQL binlog coordinates) → copy → replay backlog → caught up.

DDIA pp. 155–156

Follower failure

Catch-up recovery: ask the leader for changes since the last applied one.

DDIA p. 156

Failover

Detect (timeout ~30 s) → choose most up-to-date follower (election/controller) → reconfigure clients and the old leader.

DDIA p. 157

Failover pitfalls

Lost async writes discarded · other systems diverge (GitHub reused auto-increment keys → private data leaked via Redis) · split brain (STONITH) · timeout too short/long. Many teams fail over manually.

DDIA pp. 157–158

Replication logs

Statement (NOW()/RAND() break) · WAL shipping (byte-level, version-locked, PG/Oracle) · logical row-based (decoupled, enables CDC, MySQL binlog) · trigger-based (flexible, slow).

DDIA pp. 158–161

Eventual consistency

Async followers converge if writes stop, but “eventually” has no bound: normally < 1 s, under load seconds to minutes. Applies to async PostgreSQL/MySQL too.

DDIA p. 162

Read-your-writes

User always sees own updates. Read own-editable data from leader · leader for ~1 min after a write · replica must reach the user's last write position (LSN beats wall clock). Cross-device needs central metadata.

DDIA pp. 162–164

Monotonic reads

No going back in time for one user. Pin user to one replica (hash of user ID); reroute on failure.

DDIA pp. 164–165

Consistent prefix

Writes read in the order written (no answer before question). Problem in sharded DBs; keep causally related writes in one partition or track causality.

DDIA pp. 165–167

Design test

Ask: what if lag were minutes? If that hurts users, provide a stronger guarantee explicitly. App-level fixes are easy to get wrong.

DDIA p. 167

Multi-leader

Leader per datacenter / offline device / collaborative editor. Local writes, survives DC outage. Price: write conflicts; often bolted-on → “avoid if possible”.

DDIA pp. 168–171

Conflict resolution

Avoid (home leader per record) · LWW (loses data) · merge (CRDTs, operational transformation) · keep siblings, resolve on write/read. Amazon cart: removed items reappeared.

DDIA pp. 171–175

Leaderless (Dynamo-style)

Cassandra, Riak, Voldemort. Write to all n replicas, wait for w; read r, take newest version. No failover. Read repair + anti-entropy (Merkle trees).

DDIA pp. 177–179 · Xu p. 102

Quorums

w + r > n → read and write sets overlap. n=3,w=r=2 tolerates 1 down; n=5,w=r=3 tolerates 2. w=n,r=1 fast reads (one dead node blocks writes). Cassandra ONE/QUORUM/ALL.

DDIA pp. 179–181 · Xu p. 96

Quorum limits

Not strong consistency (Xu overstates): sloppy quorums, LWW on concurrent writes, write concurrent with read, failed writes not rolled back, restore from stale replica. No read-your-writes/monotonic guarantees.

DDIA pp. 181–182

Sloppy quorum + hinted handoff

Accept writes on stand-in nodes when home replicas unreachable; hand back later. Higher write availability; quorum reads may miss them. Riak on by default; Cassandra off (2017).

DDIA pp. 183–184

LWW

Highest timestamp wins, others silently dropped (even acknowledged ones). Safe only for write-once keys (UUID per event).

DDIA p. 186

Happens-before & version vectors

Concurrent = neither knew of the other. Per-replica counters; X before Y if Y ≥ X in every counter, else siblings to merge (union + tombstones, or CRDTs).
