Reference · Phase 2 (transactions)

Transactions & isolation

The short version of Lesson 0009. Source: DDIA Ch. 7. Second half: Lesson 0010.

Transaction

Group of reads/writes: all commit or all abort. Point of aborts = safe retry. Not a law of nature, a programming-model simplification.

DDIA pp. 221–223

A · Atomicity

“Abortability”: on failure, every write in the transaction is undone. Not about concurrency.

DDIA p. 224

C · Consistency

Your application's invariants. DB enforces only constraints (FK, unique). “Doesn't really belong in ACID.”

DDIA p. 225

I · Isolation

Concurrent transactions don't interfere. Ideal = serializable; defaults are weaker.

DDIA p. 225

D · Durability

Committed data survives: disk + WAL and/or replicas. Nothing is perfect; combine disk, replication, backups.

DDIA pp. 226–227

4 meanings of “consistency”

Replica (eventual) consistency · consistent hashing · CAP C = linearizability · ACID C = app invariants. Say which one.

DDIA p. 224

Multi-object

Denormalized counters, FKs, secondary indexes need several writes kept in sync. Single-object CAS/increment ≠ transaction. KV multi-put may partially fail.

DDIA pp. 228–231

Retrying aborts

Commit may have succeeded (dedupe / idempotency key) · overload: cap + backoff · only transient errors · external side effects not rolled back.

DDIA p. 232

Read committed

No dirty reads, no dirty writes. Writers row-lock until commit; readers get old committed value. Default: PostgreSQL, Oracle, SQL Server. Allows read skew.

DDIA pp. 234–237

Read skew

Non-repeatable read: values from different moments in one transaction (Alice's $900). Fatal for backups, exports, analytics.

DDIA Fig. 7-6

Snapshot isolation / MVCC

Each txn sees data committed before it started. Rows versioned with created_by / deleted_by txids. Readers never block writers and vice versa. GC (VACUUM) removes old versions.

DDIA pp. 238–241

Naming mess

PostgreSQL/MySQL “repeatable read” = snapshot isolation. Oracle “serializable” = snapshot isolation. DB2 “repeatable read” = serializable. Check what your level prevents.

DDIA p. 242

Lost update

Two read-modify-write cycles on the same row; second write clobbers the first. Counters, JSON list edits, wiki saves.

DDIA p. 243

Lost-update fixes

Atomic SET x = x + 1 (best) · SELECT … FOR UPDATE · auto-detection (PG repeatable read yes, MySQL repeatable read no) · compare-and-set (check snapshot semantics). Replicas: merge siblings; LWW loses updates.

DDIA pp. 243–246

Write skew

Two txns read the same condition, each writes a different row, together break the rule (doctors on call). Not caught by SI anywhere. Fix: FOR UPDATE on rows read, or serializable.

DDIA pp. 246–248

Phantoms

Check is “no matching row exists” (booking, username, double-spend) → nothing to lock. Fix: unique constraint · materialize conflicts (lock-only rows; last resort) · serializable.

DDIA pp. 249–251

Serial execution

One thread, stored procedures, data in RAM. Redis (Lua), VoltDB, Datomic. One slow txn stalls all; one core unless partitioned; cross-partition ~1k/s (VoltDB).

DDIA pp. 252–256

Two-phase locking (2PL)

Shared locks for reads, exclusive for writes, all held to commit. Readers & writers block each other. Index-range locks for phantoms. Deadlocks, bad p99. MySQL/SQL Server serializable. ≠ 2PC.

DDIA pp. 257–261

SSI

Snapshot isolation + track reads; abort at commit if premise went stale. Optimistic, no blocking, predictable latency; aborts under contention. PostgreSQL SERIALIZABLE, FoundationDB.

DDIA pp. 261–266

Always

Any of these fixes means the app must retry aborted transactions (deadlock, serialization failure).
