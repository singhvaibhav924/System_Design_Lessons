Scalability cheat sheet

The short version of Lesson 0001, for quick review.

One-line definition

Scalability = the ability to cope with a specific kind of load growth. Always say which load parameter is growing (requests/sec, read:write ratio, users online at once, data size, payload size…). (DDIA p. 10–11)

Scale up / verticalScale out / horizontal
MoveBigger machine (CPU, RAM, disk, GPU)More machines (shared-nothing nodes)
ProsSimple, no code changes, no network coordinationMuch higher ceiling, cheap standard hardware, survives losing machines or data centers
ConsHard ceiling, cost grows faster than linearly, 2× size ≠ 2× load, SPOFNetwork coordination, consistency and partial failure. Work must be splittable
Use whenEarly on, for databases until forced, GPU-bound inferenceStateless tiers, beyond one machine's limit, high-availability needs

Bottleneck

The slowest part on a request's path. It limits the whole system. Scaling anything else is wasted.

Ask first: "what saturates first at 10× load?"

SPOF

A part whose failure stops the entire system. Fix: redundancy plus failover. "Build redundancy at every tier."

Xu Ch. 1

Fault domain

A set of things that fail together: a rack, a building, an availability zone, a region. Copies only count as redundant if they're in different fault domains.

Stateful server

Remembers client data between requests in its own memory or disk. The same user must keep hitting the same server (sticky sessions). Hard to add, remove or lose servers.

Stateless server

Keeps nothing between requests and reads state from a shared store (DB, Redis). Servers are interchangeable, so they're easy to scale and autoscale.

The state moved; it didn't vanish. The data tier now has the hard problems.

Elasticity / autoscaling

Adding and removing machines automatically with load. Great for unpredictable load. Manual scaling is simpler with fewer surprises (DDIA p. 17). Watch for cold starts (e.g. loading model weights).

Xu's scaling checklist (end of Ch. 1)

  1. Keep the web tier stateless
  2. Build redundancy at every tier
  3. Cache data as much as you can
  4. Support multiple data centers
  5. Host static assets in a CDN
  6. Scale the data tier by sharding
  7. Split tiers into individual services
  8. Monitor your system and use automation tools
