Data models & SQL vs NoSQL

The short version of Lesson 0011. Sources: DDIA Ch. 2, DMLS Ch. 3, Xu Ch. 1.

Choose by relationships

Tree (one-to-many, loaded whole) → document. References (many-to-one/many) → relational. Relationship-heavy → graph.

DDIA p. 39

Normalization

Each human-meaningful fact once, referenced by ID (foreign key). Rule of thumb: duplicated values that could live in one place = not normalized. Normal forms rarely matter.

DDIA p. 33 · DMLS p. 59

Denormalization

Copy data in for cheaper reads; you must keep copies in sync (transactions, lesson 0009). Joins avoided, write work added.

DDIA p. 34

Document strengths

Locality: one read for a whole profile; less object–table translation (impedance mismatch). MongoDB, CouchDB.

DDIA pp. 30–32

Document limits

Weak joins → app-side joins or duplication. Whole document rewritten on update → keep small. Can't reference nested items directly.

DDIA pp. 38–41

Schema-on-read vs -on-write

“Schemaless” = implicit schema in every reader (dynamic typing). Relational = DB enforces (static typing). Backfill UPDATEs slow anywhere.

DDIA pp. 39–41

Graph model

Vertices + edges; variable-hop traversals (born in USA via city→state→country). Neo4j / Cypher.

DDIA p. 49 · DMLS p. 65

History & convergence

IMS (1968) = hierarchical, like JSON. Relational won via the query optimizer. Now PG/MySQL do JSON, doc DBs add joins → polyglot persistence.

DDIA pp. 36–42

NoSQL families

Key-value (Redis, DynamoDB) · document (MongoDB) · wide-column (Cassandra, HBase) · graph (Neo4j). “NoSQL” began as a 2009 meetup hashtag.

Xu p. 8 · DDIA p. 29

Interview answer

Default relational (Xu). Justify alternatives with: relationships, access pattern, transaction needs, real scale.
