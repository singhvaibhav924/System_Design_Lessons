Reference · Phase 1.5

Failure, timeout, and retry

The short version of Lesson 0005.

Partial failure

Some nodes or links fail while other parts keep working. The caller may not know which part is broken.

DDIA Ch. 8, pp. 296–299

Timeout

“I stopped waiting.” It does not prove the request did not arrive, run, or commit.

DDIA Ch. 8, pp. 300–306

Choosing a timeout

No universal value. Measure response-time variation and fit the timeout to the caller’s deadline and tolerance for delay.

Safe retries

Retry transient failures only. Cap attempts, increase the wait between them, and stop at the overall deadline.

DDIA Ch. 7, pp. 254–255

Retry danger

The first attempt may have succeeded and its response may have been lost. A retry can apply the effect twice; overload retries can add load.

Idempotent operation

Repeating the operation leaves the same final effect as doing it once. “Set status = complete” usually is; “increment counter” is not.

DDIA Ch. 11, pp. 500–501

Operation ID

Give one user action a stable ID. Carry it to the effect and enforce uniqueness atomically. Reuse the ID on retries; use a new one for a new action.

DDIA Ch. 12, pp. 539–542

“Exactly once”

Usually means duplicate attempts are suppressed so the visible effect occurs once within a stated boundary. It is not a network delivery guarantee.

Remember

A timeout creates uncertainty. A stable operation ID plus atomic deduplication makes that uncertainty safe to retry.
